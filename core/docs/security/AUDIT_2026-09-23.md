# Security audit — 2026-09-23

**Scope:** the pre-cutover security review of the Watchizer multi-storefront platform, run the day a
Phase-2 cutover was scheduled. Two jobs: three verifications that gate the cutover (Part A), then a
full security audit (Part B). The system under test: a public Next.js storefront (`Frontend-next/`),
a Laravel 13 "core" app (`core/`) that serves BOTH the storefront API on `api.watchizereg.com` and
the Inertia/React admin dashboard on `eleganceeg.com` from one document root, a still-live legacy
Laravel 10 app (`backend/`) on `dash.watchizereg.com`, one shared MariaDB with real customers and
orders, and card payments through Paymob. The repository is PUBLIC; the attacker is assumed to have
read the source.

**How to read this:** every finding says what it is, where it is (`file:line`), how it is exploited,
the evidence gathered, and the recommended fix. A later session should be able to fix from this
document without asking anything. Findings are numbered as they were reported; the numbers are
stable references, not a strict severity rank (severity is stated per finding).

**Method note (why this document trusts code over comments):** every claim here was verified against
the code and, where relevant, a running app on a scratch database — never against a docblock, a
report, or another session's summary. Where something could only be confirmed on the live host or
was asserted by a recon pass I could not independently reproduce offline, it is in the UNTESTED
section, said plainly.

# PART A — the three verifications

## A① The 134-case compat harness — FAILED (this is the cutover gate)

**Command (runbook §12):** restore the production dump into `wz_scratch`, point `core/.env` at it,
`config:clear`, prove the DB name, `migrate` → `core:drop-clean` → `migrate` → `core:transform`,
then `pwsh -File scripts/run-compat-harness.ps1`. **Pass condition:** `134 cases, PASS`, every
difference on a rule in `App\Compat\Diff\DeviationRules`.

**Result: FAIL — 9 unexplained differences in 9 cases.** Report:
`core/storage/compat-diff/20260923-150801/report.md`. Two independent causes.

### Cause 1 — English validation text leaks the dashboard's attribute labels (2 cases)

- **Cases:** `cart:remove:bad-type`, `checkout:bad-method`.
- **Where:** `core/lang/en/validation.php:219` (`'product_id' => 'Product'`) and `:261`
  (`'payment_method' => 'Payment method'`). The legacy app ships `'attributes' => []`
  (`backend/lang/en/validation.php`), so Laravel auto-humanises the field name.
- **The diff:**
  - `errors.product_id[0]`: legacy `The product id field must be an integer.` vs core
    `The Product field must be an integer.`
  - `errors.payment_method[0]`: legacy `The selected payment method is invalid.` vs core
    `The selected Payment method is invalid.`
- **Why it appeared now:** the 2026-09-23 fix made `add_address`, `remove_from_cart` and `add_order`
  negotiate `Accept-Language` (default `en`). Core's `attributes` map — added for the dashboard's
  English operators — now reaches the shopper. `D-25` sanctions Arabic phrasing only, so the English
  divergence is (correctly) still a failure.
- **Developer decision (2026-09-23):** ACCEPT. Core's attribute map reads better than the raw field
  name and exists for the dashboard's operators. **Fix to apply:** widen the deviation rule so the
  harness stops failing on it — extend `D-25` (or add a sibling rule) in
  `core/app/Compat/Diff/DeviationRules.php` to cover the `errors.*` phrasing divergence on these
  three routes in **both** languages, keeping the existing scoping (a difference in `message`, the
  status, or the field KEYS is still a failure). Record the acceptance and the reason beside the
  rule.

### Cause 2 — the rebuild lets a repair migration seize brand id 1 (7 cases)

- **Cases:** `meta`, `meta:ar`, `meta:fr`, `meta:no-accept`, `meta:any-accept`,
  `meta:cors:storefront-origin`, `meta:cors:foreign-origin`.
- **The diff:** `$.tables.brands[0].created_at` — legacy `2026-07-19T01:14:41Z` vs core
  `2026-09-23T12:05:48Z` (i.e. `now()` at rebuild time).
- **Mechanism (proven on the scratch data):**
  1. `core:drop-clean` empties `catalog_brands`.
  2. `migrate` runs `core/database/migrations/2026_10_04_000000_restore_electronics_and_joyroom.php`,
     whose `joyroomBrand()` (~:97) `insertGetId(['slug'=>'joyroom', ..., 'created_at'=>now()])` into
     the now-empty table — taking **id 1**.
  3. `core:transform` `core/app/Transform/Steps/Step01Brands.php:77` upserts the 77 legacy brands
     keyed on `id` with the update list `['slug','logo_path','is_active','updated_at']`. Legacy brand
     1 is **Rolex**. Row 1 is overwritten as Rolex, but `created_at` is not in the update list, so the
     migration's `now()` survives.
- **Evidence:** on `wz_scratch` (rebuilt), `catalog_brands` id 1 = `rolex`,
  `created_at 2026-09-23 15:05:48`; `SELECT … WHERE slug='joyroom'` returns nothing; clean brands
  count 77 = legacy 77. On the local dev DB `u591083448_watchizer`, where the migration ran AFTER the
  catalogue was populated, joyroom is id 185, clean brands = 79, and brand 1 carries the correct
  legacy `created_at`. So the collision is a property of the rebuild order, not of the data.
- **The general defect:** a data-repair migration is a silent no-op on an empty catalogue. The same
  rebuild reported `re-branded 0 products; mirrored 0 electronics nodes; placed 0 products` and
  `merge_model_number_into_sku … 0 products` — every repair migration that reads existing rows does
  nothing when `migrate` runs before `core:transform`.
- **Developer decision (2026-09-23):** there will be **no further rebuild** — the team is already
  authoring in the dashboard and `core:drop-clean` would destroy their work. **Fixes to apply:**
  1. In `core/docs/deploy/RUNBOOK_PHASE2_STOREFRONT.md`, **remove §3.4 step 3b (the drop-and-rebuild)
     entirely** and replace it with an explicit prohibition and the reason: the clean tables now hold
     human work; a rebuild erases it (this is the "point of no return" already recorded in
     `AGENTS.md` §6). 
  2. Add `'created_at'` to the `Step01Brands` upsert update list so the contract diff cannot recur if
     a rebuild is ever run in a non-production context.
  3. Leave a one-line guard note by the repair migrations: they are no-ops on an empty catalogue and
     must run after `core:transform`, not before — so the next repair written the same way is not
     silently inert.
- **Answer to "does the brand `created_at` diff matter once no rebuild is possible?"** No, not by
  itself: with the rebuild retired, `catalog_brands` is populated once and never re-seized, so the
  id-1 collision cannot recur and the timestamp is cosmetic. But Cause 1 (English text) is a live
  divergence on the running app regardless of rebuilds and still needs the D-25 widening; and the
  "repair migration is a silent no-op" class is worth the guard note above.

## 🔴 Finding 1 — a storefront-scoped admin becomes a global admin, permanently (privilege escalation)

**Severity: Critical.** **Where:** `core/app/Domain/Access/Roles.php:64,45`,
`core/app/Domain/Access/Abilities.php:23`, `core/app/Http/Controllers/Manage/UserRoleController.php:131,177,216`.

**What it is.** Role grants can be scoped to one storefront (`core_user_roles.storefront_id`), but the
admin short-circuit is scope-blind:
- `Roles::isAdmin()` → `rolesFor()` collects roles **without ever reading `storefront_id`**
  (`Roles.php:45-56,64-67`).
- `Gate::before` (`Abilities.php:23-31`) returns `true` for any ability in `Role::ABILITIES` whenever
  `isAdmin()` is true. It never reaches the scoped `Gate::define` closure.
- `Role::Admin => self::ABILITIES` (`Role.php:225`) — an admin holds every ability, `manage-users`
  included.
- Only 4 of 19 `/manage` route groups carry `EnsureStorefrontScope` (which correctly calls
  `Roles::can()` directly and bypasses the Gate). Every other `/manage` route is a `can:<ability>`
  question asked with **no** `{storefront}` argument, so a scoped admin passes it globally.

**How it is exploited.**
1. A storefront-2-scoped admin (e.g. a Brand Fashion manager — creatable through the very forms
   below, which accept `role=admin` + any `storefront_id`) reaches `can:manage-users` because that
   route asks the unscoped question.
2. `UserRoleController::store()` (`:131`) validates `role ∈ {admin, data_entry}` and `storefront_id`
   as any existing storefront, with **no check that the actor's own scope permits it**. The scoped
   admin POSTs `{role: admin, storefront_id: null}` → grants itself an **unscoped** admin.
   `storeAccount()` (`:177`) is the same hole with a fresh account attached.
3. `destroy()` (`:216`) loads a grant by primary key with **no actor-scope predicate**; the only
   guards are self-revoke and last-unscoped-admin. The scoped admin walks grant ids and revokes every
   other operator.
4. With global admin they can also rename/disable the live Watchizer storefront
   (`manage.storefronts.*`, `web.php:82-86`, `can:manage-storefronts` only — no scope middleware),
   taking the shop down.

**Evidence.** Read `Roles.php`, `Abilities.php`, `Role.php`, `UserRoleController.php` in full;
confirmed `rolesFor()`/`isAdmin()` never reference `storefront_id`, that `Role::Admin` holds
`MANAGE_USERS`, and that all three write methods lack an actor-scope check.

**Fix.**
- `Abilities.php` `Gate::before`: return `true` only for an **unscoped** admin —
  `$roles->isAdmin($user) && $roles->storefrontScope($user) === null`; otherwise `return null` to
  fall through to the scoped `Gate::define` closure.
- `UserRoleController::store/storeAccount/destroy`: read `Roles::storefrontScope($request->user())`
  and refuse any `role`/`storefront_id` wider than the actor's scope (a scoped admin may grant only
  within its own storefronts and may never grant `storefront_id = null`). Narrow the `storefronts[]`
  prop the form offers to match.
- Add a test that a storefront-scoped admin is refused `manage-users`, refused an unscoped grant, and
  refused revoking a grant outside its scope.

## 🔴 Finding 2 — anonymous PII disclosure + order/stock IDOR on `POST /api/add_order`

**Severity: Critical.** **Where:** `core/app/Http/Controllers/Compat/CheckoutCompatController.php:101-127,796-818,174-179`,
`core/app/Compat/CompatCheckout.php:107-118,26-29`, `core/app/Compat/CompatAccount.php:153-158,177-182`.

**What it is.** The checkout endpoint (unauthenticated `compat.guest` group) takes the buyer and the
address from the request body and dereferences them into real PII with no ownership check.
- `user_id` and `address_id` come from the body; `address_id` is validated
  `exists:addresses,id` only, with **no ownership predicate** (`:102-103,126-127`).
- `billingData()` (`:796-818`) loads `users` by `user_id` and `addresses` by `address_id` and returns
  `{first_name,last_name,street,phone_number,city,country,email}`; `paymob()` ships it to Paymob and
  returns the hosted-checkout `redirect_url` **to the caller**, who opens it and reads the victim's
  details rendered on it.
- `me/orders` → `CompatAccount::addressRowsById()` (`:158`) is `whereIn('id', $addressIds)` with **no
  `user_id`**, and `addressRow()` (`:182`) emits `guest_token` — a bearer credential for
  `GET me/cart` and `POST cart/merge`. So: place an order with someone else's `address_id`, then
  `GET me/orders` reads their `address_line`, phones, city, and `guest_token` back → guest-cart
  takeover.
- The total guard is an oracle: `:174-179` returns `server_total`, which includes
  `shippingCost($addressId)` — an unowned `addresses → shipping_cities` join
  (`CompatCheckout.php:112-115`) — so one wrong request discloses the victim's governorate shipping
  cost (hence governorate) anonymously.
- Side effects: a COD order calls `mailer->placedNow(..., notifyCustomer: true)` (victim gets a
  confirmation for an order they did not place) and reserves real stock through `InventoryService` (a
  no-throttle inventory DoS at 60 req/min).

**How it is exploited.** Anonymous caller enumerates sequential `address_id`s (the `exists` rule is
itself an oracle) and `user_id`s, POSTs `add_order`, opens the returned `redirect_url` to read PII;
or places an order against a victim's address and reads it back via `me/orders` together with the
guest token.

**Evidence.** Traced the full chain in source. The class docblock at `CompatCheckout.php:26-29`
assesses the `user_id` weakness as "mis-attribution rather than disclosure" — that assessment is
stale: `billingData()` reads the rows and puts them on a page the caller opens, and
`addressRowsById()` reads them straight back. I did **not** stage a live extraction against the real
customer rows in the scratch DB (deliberately).

**Fix (any one of the first two breaks the chain; do all four).**
1. Take the buyer from the JWT only: `$userId = LegacyJwt::userId($request);` and ignore the body
   field (`AccountCompatController.php:44` already prefers the JWT — make it exclusive).
2. After resolving `$addressId`, assert ownership before use:
   `DB::table('addresses')->where('id',$addressId)->where(fn($q)=>$q->where('user_id',$userId)->orWhere('guest_token',$guestToken))->exists()` or reject.
3. Drop `guest_token` from `CompatAccount::addressRow()` (`:182`) — no storefront screen reads it.
4. Add `->middleware('throttle:add-order')` to the route.
   (`server_total` is legacy-parity, so leave it; fix #2 makes the oracle moot.)

**Related — `POST /api/add_address`.** `core/app/Http/Controllers/Compat/AccountCompatController.php:44-48`
writes `user_id` from the body with `'user_id' => 'nullable|integer'` (no `exists`), so an
unauthenticated caller drops an address into any victim's address book (delivery redirection). Fix:
delete the body fallback — a genuine guest already gets `user_id = null` + `guest_token`.

## 🟠 Finding 3 — stored XSS on every listing page → 30-day account takeover

**Severity: High.** **Where:** `Frontend-next/src/lib/facetListing.jsx:62`,
`Frontend-next/src/lib/listingSeo.js:109-127,228-238`, token storage
`Frontend-next/src/Context/api.jsx:16`.

**What it is.** `facetListing.jsx:62` renders
`<script type="application/ld+json" dangerouslySetInnerHTML={{ __html: JSON.stringify(breadcrumbLd) }} />`.
`JSON.stringify` does **not** escape `<`, `>` or `/`. `breadcrumbLd.itemListElement[1].name` is
`crumb = listingCrumbEn(tables, filters)` — a **stored** DB name
(`nameEn(category/subType/brand/grade, …_name)`, `listingSeo.js:109-127`). A category/sub-type/brand/
grade whose English name contains `…</script><img src=x onerror=…>` breaks out of the JSON-LD block
and executes on **every** listing/facet page of the public storefront.

**How it is exploited.** Set a lookup/category/brand/grade name (via the dashboard lookups/category
screens or the importer — the same write surface Finding 1 widens) to a payload closing the
`</script>` and opening an attacker script. On every visitor's listing page it runs. Because the
customer JWT lives in `sessionStorage` (`api.jsx:16`, readable by any script) with a 30-day TTL, the
payload reads and exfiltrates it → customer-account takeover for up to 30 days; the guest token
(localStorage) goes too.

**Evidence.** Read `facetListing.jsx`, `listingSeo.js`, and `api.jsx`. This is the ONLY JSON-LD sink
of this shape in the app (grep for `application/ld+json` / `JSON.stringify` into a script returned one
hit). The product-description sink is separately safe (Finding-clean list below).

**Fix.** Escape before injection — replace `<`→`\u003c`, `>`→`\u003e`, `&`→`\u0026` in the
stringified JSON (a small `safeJsonLd(obj)` helper), or use a vetted JSON-LD component. This is the
standard hardening for `dangerouslySetInnerHTML` JSON-LD.

## 🟠 Finding 4 — legacy API gate fails open when the key is empty

**Severity: High.** **Where:** `backend/app/Http/Middleware/CheckApiMiddleware.php:18-20`,
`backend/config/services.php:34`, `backend/.env.example:64`.

**What it is.** `if ($request->header('Api-Code') == $apiPassword)` with `==`. `public_api_key` has no
default; unset → `null`; a request with no `Api-Code` header → `null`; `null == null` is true. If set
to empty string (which `backend/.env.example:64` ships — `PUBLIC_API_KEY=`), `null == ''` is also
true. Either way every `CheckApi` route on the live legacy host opens to a caller sending **no header
at all**. Core's equivalent (`core/app/Http/Middleware/CheckApiCode.php:22`,
`$expected !== '' && $request->header('Api-Code') === $expected`) is correctly guarded; the legacy
host never got the fix, and `backend/` is the documented rollback target.

**Evidence.** Read both middlewares; confirmed the `==` and the empty default.

**Fix.** `if (is_string($apiPassword) && $apiPassword !== '' && hash_equals($apiPassword, (string) $request->header('Api-Code')))`
— the emptiness guard (the bug) plus `hash_equals` (hygiene).

## 🟠 Finding 5 — legacy `/register` is open and unthrottled on the dashboard host

**Severity: High (cross-app).** **Where:** `backend/routes/auth.php:15-18`.

**What it is.** Breeze's `GET|POST /register` is live on `dash.watchizereg.com` — anonymous,
unthrottled writes into the shared production `users` table. `type` defaults to `User`, so it grants
no dashboard access (core's `EnsureDashboardAccess` refuses it), but it is anonymous row-creation in
the table holding every real customer, and that table is also core's.

**Evidence.** Read `backend/routes/auth.php`; confirmed the route is registered (not commented).
Confirms the two-app shared-DB concern: the legacy app can write the shared `users` and commerce
tables, and it also carries Finding 4's fail-open gate.

**Fix.** Disable or heavily throttle legacy `/register` before/at cutover. (Core's `UserWriteGuard`
cannot constrain the legacy app; only closing legacy's own routes can.)

## 🟡 Finding 6 — the `cp -a` window in runbook §2.4 briefly opens `/api` on the API host

**Severity: Medium (live window).** **Where:** `core/docs/deploy/RUNBOOK_PHASE2_STOREFRONT.md` §2.4;
`core/public/.htaccess` (currently stock Laravel, no `/api` block).

**What it is.** Before §4 is applied, `/api` is kept shut on both hosts by the pre-existing eleganceeg
`.htaccess` blanket rule `RewriteRule ^api(/|$) - [R=404,L]` (host-agnostic, so it blocks
`api.watchizereg.com` too). §2.4's `cp -a` overwrites that with core's stock `.htaccess` (no `/api`
block) and restores it "in the same breath". For the length of that one `cp`, `/api` is OPEN on
`api.watchizereg.com`. Combined with the public API key shipping in the storefront bundle (so
`api.code` is no barrier to a repo-reader) and Finding 2, a reader of the public repo can hit
`POST /api/add_order` during that window.

**Evidence.** Confirmed the current `core/public/.htaccess` is stock Laravel with no `/api` block.
The developer verified on the live hosts (2026-09-23, from SSH) that both
`https://eleganceeg.com/api/all_product` and `https://api.watchizereg.com/api/all_product` return
404 and that `core/public/.htaccess` line 7 holds the blanket block — so the blanket-block assumption
holds server-side today; the `cp` window is the residual. This measurement was recorded in the
runbook §2.4.

**Fix.** Keep the window to a single `cp` and run the two verification curls immediately after, as the
runbook now states. (No code fix; procedural.)

  `'secure' => env('SESSION_SECURE_COOKIE')`). If unset on the HTTPS server, the dashboard session

- **CORS `exposed_headers => []`** (`core/config/cors.php:31`) while the guest cart depends on the

## Tested — clean, with evidence

### Payment and callback attacks — clean
`php vendor/bin/pest tests/Feature/Payment tests/Feature/Compat/PaymobCallbackTest.php` → **78 passed**.
Coverage maps to every attack in the brief (real assertions, not comment claims):
- Forged signature → 403 before any write; tampered fields → bad-sig
  (`hash_hmac('sha512', concat(20 signed fields), hmac_secret)` compared with `hash_equals`,
  `PaymobProvider.php:161-187`).
- Replay → idempotent via `UNIQUE(provider, pay_transaction_id)`, checked before and enforced under
  the insert; second delivery → 200 "already processed".
- Forged payload for another merchant → `CallbackChecksTest` "two storefronts cannot validate each
  other" (each verifies with its own contract secret, never a global one).
- Payload for another storefront → `CHECK 3` ownership (order `storefront_id` must equal the route's;
  the unsigned `merchant_order_id` is made safe by this check plus preferring the signed `order`
  field, `PaymentCallbackController.php:421`).
- Order not in a payable state → `TerminalStateCallbackTest`: refuses every state beyond `processing`;
  decline-then-succeed does not resurrect a cancelled order or re-reserve stock; refund/void never
  counts as revenue.
- Amount mismatch → record-only, order untouched, fail-closed (1-cent rounding tolerated).
- No HMAC secret → fail-closed.
- Deviation: `storefront_id IS NULL` legacy orders accepted as the primary storefront only, logged,
  with a written sunset. The live Watchizer alias falls through to the proven wave-3 handler until the
  contract is complete (Part A③).

### SQL injection — clean
The request-reachable query surface is parameterised or allow-listed end to end:
- `core/app/Support/Table/TableQuery.php`: sort resolves a public name against a caller-declared
  whitelist (`sortNames`/`sortable`, unknown → default sort, `:395-409`); direction
  `in_array(['asc','desc'])` (`:422`); search `where(col,'like','%'.escapeLike(term).'%')` bound, with
  `% _ \` escaped (`:487,617-619`); filter values bound and filter COLUMNS are caller-declared keys,
  never request strings (`:444-459`).
- FULLTEXT search binds: `whereRaw('MATCH(s.body) AGAINST (? IN BOOLEAN MODE)', [booleanTerm($term)])`
  (`core/app/Domain/Catalog/ProductSearch.php:87`).
- The only raw-SQL interpolations in `app/` are `Sql::delta()` / `eitherBucketPositive()` (column via
  `in_array(self::COLUMNS)` allow-list, delta typed `int`) and `Sql::jsonExtract()` (column
  allow-listed, values bound) — `core/app/Support/Sql.php:45-72,236`. `AuditRunner.php:413`
  interpolates a pivot FK from fixed config, transform-only, not request-reachable.
- Bulk id lists go through `Coerce::intList()` → every element `nint()`-narrowed before `whereIn`
  (`core/app/Support/Coerce.php:156-167`).

### Stock, pricing, and promotion abuse — clean
`php vendor/bin/pest tests/Feature/Inventory tests/Feature/Compat/CartCheckoutTest.php` → 108 passed;
`tests/Feature/Promotions` → 88 passed.
- Tampered total → `add_order` "prices every line from the catalog and refuses a client total that
  disagrees" (server recomputes; the client total is advisory).
- Stock negative / concurrent checkout → "refuses an order the bucket cannot cover, persists nothing";
  `ExactlyOnceTest` + single lock order (`orders → catalog_products → catalog_product_variants`) +
  unique-constrained ledger; cancellation restores through `InventoryService`, never a column write.
- Promotion abuse → `PromotionScenarioTest:345` "refuses a rule with NO conditions, which would
  otherwise apply to every cart"; unsellable/no-stock/not-visible gifts refused;
  `StorefrontIsolationTest` reads the storefront pivot as an INNER JOIN so a Brand Fashion rule cannot
  touch a Watchizer cart.
- Variant → an inactive variant cannot be sold (negative `order`/`promotion_reward` movement refused).

### CSV formula injection — clean
`core/app/Support/Table/TableExport.php:defuse()` prefixes any cell starting with `= + - @ \t \r`
with an apostrophe, applied to every cell in the one shared exporter (`:79`, inside the `fputcsv`
loop). Two console-only CSV writers (`ArchiveSlugsCommand`, `CoreTransformCommand`) do not defuse, but
they are operator diagnostics written to disk, not victim-facing downloads — low note.

### CSRF, token storage, OAuth login-CSRF, CORS — clean
- **Dashboard CSRF:** the Laravel `web` middleware group is used
  (`core/bootstrap/app.php:26`) with **no `$except`** list anywhere; session cookie `HttpOnly=true`
  (`config/session.php:185`), `SameSite=lax` (`:202`); Inertia sends the token.
- **Storefront:** the customer JWT is sent as `Authorization: Bearer` from `sessionStorage`
  (`api.jsx:16`), no auth cookies, so CSRF does not apply. (Note the XSS→token chain in Finding 3:
  `sessionStorage` is XSS-readable and `JWT_TTL` is 30 days.)
- **OAuth login-CSRF:** `->stateless()` (which removes the state check) is correctly replaced by an
  SPA-generated nonce, HMAC-signed by core into `state`, echoed by the provider, and compared
  SPA-side against `sessionStorage` (`core/app/Domain/Customers/SocialNonce.php`,
  `Frontend-next/src/lib/socialNonce.js`). Sound design.
- **CORS:** exact origin allow-list — `watchizereg.com`, `www.`, `dash.`, localhost only when local
  (`config/cors.php:19-26`); `allowed_origins_patterns => []`; `supports_credentials => false`. No
  origin spoofing possible (`watchizereg.com.evil.com` will not match). Only issue is
  `exposed_headers => []` (Finding 9).

### The `users` write guard — thorough; escapes are the cross-app ones
`core/app/Domain/Access/UserWriteGuard.php` closes the table at `Connection::beforeExecuting()` (the
door, pre-send) over select/insert/update/delete/statement/affectingStatement/unprepared, plus a
`QueryExecuted` net; DELETE is refused absolutely. The only escapes it documents are (a) raw
`PDO::exec()` on a `DB::getPdo()` handle — a grep of `core/app/` shows the only occurrences are the
guard's own docblocks, so no such path exists in core code; it needs attacker code-execution, and (b)
out-of-process writers (the legacy app, a `mysql` client) — by design, which is why Finding 5 (legacy
open register) matters.

### Product-description XSS sink — clean
`Frontend-next/src/Components/Product/ProductDetailClient.jsx:1328` renders `descHtml`, which is
`DOMPurify.sanitize(description)` (`:634`, default config) computed client-side after mount; during
SSR `descHtml` is empty, so no unsanitised HTML is ever server-rendered. Review comments are
sanitised the same way (`:665`). The nav brand-logo `innerHTML` (`Nav.jsx:314`) injects a 2-char
uppercased `initials` substring — two chars cannot form a working tag; not exploitable, but prefer
`textContent` as defense-in-depth.
