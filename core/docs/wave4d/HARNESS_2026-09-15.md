# The compat harness: what stopped it, and how to run it

**2026-09-15 — the harness ran end to end for the first time since wave 4B. 127 cases, 0 unexplained
differences.**

---

## Run it

```powershell
pwsh -File scripts/run-compat-harness.ps1
```

That is the whole recipe. The script boots both hosts, verifies them, runs `compat:diff`, and stops
them again — including the `artisan serve` **child** processes, which is what used to leave a port
held and produce the next run's "port already in use" mystery.

| flag | what it does |
| --- | --- |
| `-SkipRun` | boot and verify both hosts, then wait — for debugging the environment alone |
| `-Pace 120` | milliseconds before each legacy request; raise it if a run starts failing on 429s (legacy throttles 60/min per IP) |
| `-LegacyPort` / `-CorePort` | defaults 8011 and 8001 |

**Prerequisites, and all of them:** PHP 8.3 at `C:\tools\php83\php.exe`, `vendor/` installed in both
apps, and XAMPP MySQL running. The script checks each one and names the missing one rather than
failing later for a reason that looks like a code defect.

---

## What had actually been wrong

The reviewer's report said "environment issues", which is accurate and — as it turns out — is the
whole problem stated precisely: the boot recipe existed only in people's heads, so an environment
that was *almost* right failed in a way that looked like the harness being broken.

There was one concrete defect underneath it:

> **`backend/.env` is the production file.** It names the right host, the right port and a database
> whose name the local copy shares — but it authenticates as the **production database user**, which
> does not exist in the local MariaDB. Every DB-touching legacy request therefore answered 500:
>
> ```
> SQLSTATE[HY000] [1045] Access denied for user '<production user>'@'localhost'
> ```

That failure is invisible from outside. The process starts, the port listens, `artisan serve` reports
nothing, and `/api/catalog/meta` answers — so every "is it up?" check passed. The first thing that
noticed was the harness's own token pre-flight:

```
Pre-flight: the two hosts answered the same authenticated request differently before any case ran
(legacy 500, compat 200). That is an environment problem, not a compat difference; fix it first.
```

The pre-flight was right, and it stopped for the right reason. What it could not do was fix it.

**The fix:** the launcher now reads the LOCAL database credentials from `core/.env` at run time and
sets them in the process environment both servers inherit. For core they are the values it already
uses, so nothing changes; for legacy they replace the production ones. Nothing is printed, nothing is
written to a file, and the production credentials in `backend/.env` are neither read nor used.

An empty local password is passed as Laravel's own `(empty)` sentinel. This matters more than it
looks: a Windows environment variable cannot hold an empty string — assigning `''` deletes it — and a
deleted variable falls straight through to the `.env` file, which is the production password again.

---

## Three guards the run now carries

1. **A cached config is refused, not cleared.** `config:cache` bakes `env()` into
   `bootstrap/cache/config.php`, after which Laravel never reads the process environment again. That
   would not merely un-fix the database: it would quietly restore `MAIL_MAILER=smtp`, which is the
   only thing standing between a harness run and four real administrators receiving mail about a test
   order (as happened on 2026-09-13, order 3381). Deleting somebody's cache behind their back is its
   own bug, so the script names the file and stops.

2. **"Live" now means answering *well*.** The old check accepted any HTTP response, which is exactly
   how a host with no working database passed as healthy — it was listening, and it replied 500 to
   everything. A 5xx on `/api/catalog/meta` now fails the boot and names the log file to read.

3. **A non-local `DB_HOST` is refused outright.** This harness places real COD orders. Discovering
   mid-run that `core/.env` had been re-pointed is the worst possible way to learn it.

### What this run is evidence of, and what it is not

It is evidence that core answers all 127 legacy cases with no difference that is not already written
down and sanctioned — over **this** catalogue, on **this** database, today. The cart and account
cases in particular had never actually executed before: the pre-flight had been stopping the run
before it reached them.

It is not a standing guarantee. The contract has to be re-proved on a rebuilt catalogue before switch
night, and the run is cheap now — one command.

## Run them in this order: REBUILD → BATTERY → HARNESS

When you are proving the whole thing — a rebuilt catalogue, a green suite and a clean harness — the
order is not free. Do it this way:

```powershell
# 0. (optional) refresh the legacy data from a production export first — see below
pwsh -File scripts/refresh-legacy-from-export.ps1 -Export "D:\...\u591083448_watchizer 9-17.sql"

# 1. rebuild
php artisan core:drop-clean --dry-run     # read the list before destroying anything
php artisan core:drop-clean --force
php artisan migrate --force
php artisan core:transform --audit        # abort on any blocking code
php artisan core:transform --force

# 2. battery
vendor/bin/pest                            # + phpstan, pint, tsc, npm run build

# 3. harness
pwsh -File scripts/run-compat-harness.ps1
```

### Step 0 — refreshing the legacy tables from a production export

`scripts/refresh-legacy-from-export.ps1`, because `mysql < export.sql` is wrong three ways and the
third one fails almost silently (all three measured 2026-09-17):

1. A phpMyAdmin export carries **no `DROP TABLE`**, so a straight import dies on *table already
   exists* for all 65 legacy tables.
2. It writes `CREATE TABLE` **without the primary key** and adds it in a later `ALTER TABLE`. Six
   core-owned foreign keys point at `users.id`, so recreating `users` makes InnoDB validate those
   orphaned child constraints against a table that has no index on `id` yet, and it refuses the whole
   statement with `errno: 150 "Foreign key constraint is incorrectly formed"`. **`SET
   FOREIGN_KEY_CHECKS = 0` does not prevent this** — it suppresses row checks, not the structural
   validation of a pending constraint's parent. The 64 other tables import, `users` does not, and the
   error is four lines deep in thousands of output.
3. Dropping those six keys is therefore required — and re-adding them is the half that gets
   forgotten. A database whose core tables have quietly lost their keys into `users` looks perfectly
   fine until somebody deletes a user.

The script drops the six, replaces the 65, restores the six, then **proves** both halves: every
core-owned table still present, every exported table present, and a before/after row count per table.
It refuses to import if its own `mysqldump` backup failed.

It leaves the database exactly where switch night starts. It does not run the transform.

### Why, and what it looks like when you get it wrong

**The harness places real orders.** `checkout:cod` and `checkout:cod:auth` are real `add_order`
calls against the local database — that is the point of them — and each writes order movements into
`inventory_movements`.

`core:transform` refuses to re-baseline over real stock movement. That is the wave-3 guard and it is
correct: once a customer order has moved stock, an opening baseline would overwrite history. So the
~31 tests that exercise the transform **skip themselves** when the ledger holds non-transform rows,
and they say so:

> `ledger holds 2 non-transform row(s) (order × 2); core:transform refuses to re-baseline over real
> stock movement — that is the wave-3 guard, not a bug. Rebuild the clean tables and run the suite
> again.`

Run the battery **after** the harness and you get **38 skipped instead of 7** — a green suite that
quietly stopped exercising the transform. Nothing fails, nothing is broken, and the number is the
only sign. Measured 2026-09-16: 1,193 passed / 7 skipped in the right order, 1,162 passed /
38 skipped in the wrong one.

The 7 that skip in either case are the `CAPTURE_SCREENS=1` evidence captures, which are opt-in.

**If you only want the harness**, none of this matters — run it on whatever catalogue is there. The
ordering is for the full proof.

## After a run: which tables are EXPECTED to have moved

**`legacy products.stock` moves, and that is the harness working, not core writing to legacy.**

This one has been misread twice, so it is written down here rather than rediscovered. The harness
drives the same checkout against **both** hosts. The legacy host is the legacy application: when it
takes a COD order it decrements its **own** `products.stock` and `products.market_stock`, exactly as
it does for a real customer. That is the behaviour under test — core has to match it.

So after a harness run:

| table | expected to change? | why |
|---|---|---|
| `products.stock`, `products.market_stock` | **YES** | the LEGACY host decremented them, serving the harness's checkouts |
| `orders`, `order_items`, `carts`, `addresses` | **YES** | both hosts placed real orders; ~12 orders per two runs, measured 2026-09-15 |
| `integration_outbox` | **YES**, all rows PARKED | 🟠-5: nothing here is ever sendable |
| every other legacy table | **NO** | core writes none of them |

**The gate is `core:checksum --set=legacy --json`, compared around the night's work — and the
comparison to make is of the tables core is supposed to leave alone.** A digest taken before and
after a harness run will differ on the commerce tables above every single time; that is not a
finding. Reading it as one is how an hour goes missing at 02:00.

What WOULD be a finding: a change in a legacy table the harness does not touch — `categories`,
`sub_types`, `colors`, `sizes`, `brands`, `product_variants`, the translation tables. Those are the
frozen set, and core writing to any of them is the thing the checksum exists to catch.

**And take the baseline AFTER `migrate`, never before it** — the separate trap already recorded in
CLEAN_CORE_STUDY §3.4, for a different reason (three tables change definition, not content).
