# Dashboard language switch — the measured cost, and the order to do it in

**Recorded 2026-09-14. Decision: NOT built in wave 4D. Post-launch backlog item.**

The developer asked for an English toggle alongside Arabic, and asked first for the honest size of
the job rather than a half-built one. This is that number, the order I would do it in, and the one
cheap step that is separable.

---

## 1. What exists today: nothing

| Fact | Value |
|---|---|
| `lang/` directory | **absent** |
| `__()` / `trans()` / `@lang` call sites in the whole application | **2** |
| Front-end i18n library | none |
| Locale stored per user | **yes, since M1m** — `core_user_preferences.locale`, written by the profile screen |

So the dashboard is **0% translatable**. The switch is not a toggle to wire up; it is a translation
project with a toggle at the end of it.

The one piece that IS done is the storage: an operator can choose `ar`/`en` on their profile today,
it persists, and it is read by `Preferences::localeFor()`. Everything below is about making screens
honour it.

## 2. The size, measured

Counted by scanning every `.tsx`/`.php` source for runs of Arabic text **with comments stripped**,
so a docblock explaining a rule is not counted as a user-facing string.

| Surface | Files | Distinct strings |
|---|---:|---:|
| React screens & components | 36 | **780** |
| Domain writers (validation refusals) | 25 | **320** |
| Controllers (flash messages, labels, options) | 17 | **219** |
| `config/*` (option labels) | 3 | **72** |
| Blade (order-mail templates, app shell) | 3 | **24** |
| Support | 2 | 5 |
| Console commands | 2 | 2 |
| **Total** | **88** | **1 422** |

Heaviest single files: `Orders/Show.tsx` (118), `Products/Form.tsx` (82), `Products/Index.tsx` (79),
`Payments/Index.tsx` (78), `Categories/Index.tsx` (72).

### The trap in that number

**320 of those strings are domain-writer refusals, and they are not dashboard strings.**
`ProductWriter`, `BannerWriter`, `InventoryService` and the rest throw Arabic `ValidationException`
messages, and those same writers answer the **compat API**, where the reader is a CUSTOMER, not an
operator. Translating them against `Preferences::localeFor($user)` would make a customer-facing API
message depend on which staff member last logged in.

So they need a different treatment from the other 1 102: a refusal must carry a **key** and the
caller must localise it — the dashboard against the operator's locale, the API against the
request's. `MediaAudit` already does exactly this (it returns `['code', 'en', 'ar']`), which is the
pattern to copy. **This is the part that makes the job a project rather than a sweep**, and it is
why I would not start with it.

The 24 Blade strings are the order e-mails, and they follow the **order's** locale, never the
operator's. Same reasoning, already correct today.

## 3. Proposed order

Each step is shippable on its own and leaves the dashboard working.

| # | Step | Strings | Why here |
|---|---|---:|---|
| **0** | **The seam** — share a `translations` prop + a `t(key, fallback)` helper that falls back to the literal | 0 | Nothing changes visually. From then on a new string is written translatable at no cost, and the backlog stops growing. Separable — see §4 |
| 1 | Shell: nav, header, user menu, breadcrumbs, the locale toggle itself | ~40 | Proves the mechanism end to end on the page every screen shares, and gives the profile setting a visible effect |
| 2 | Shared primitives: `DataTable`, `ExportLink`, empty states, filter labels, pagination | ~120 | One edit improves **every** screen at once |
| 3 | Screens by traffic: Products, Orders, Inventory, Categories/Placement | ~450 | The four the team lives in |
| 4 | Remaining screens: Payments, Promotions, Banners, Customers, Users, Lookups, Units, Media | ~330 | |
| 5 | Controller flash messages + `config/*` option labels | ~290 | Server-side, mechanical, `__()` works today with no new infrastructure |
| 6 | **Domain refusals → keys** | ~320 | Last, deliberately: it changes a contract the compat API depends on and wants its own review |

Steps 1–4 are where the translation-quality question lives — English labels for a shop's
vocabulary (`إكسبريس`/`ماركت`, family names, order statuses) are a decision for whoever writes the
English copy, not a mechanical transform. I would want that glossary agreed before step 3.

## 4. The cheap first step, costed separately

**Step 0 alone**, which the developer asked to have priced on its own.

What it is:

- `lang/ar/manage.php` + `lang/en/manage.php` (start empty);
- `HandleInertiaRequests` shares `locale` (from `Preferences::localeFor()`) and the flat
  `translations` map for that locale;
- a ~40-line `t(key, fallback)` helper in `resources/js/lib/`, where **the fallback is the current
  literal**, so `t('banners.state.running', 'ظاهر الآن')` renders correctly on day one with no lang
  file at all;
- `__()` used for new server-side strings, which needs no new infrastructure whatsoever.

What it costs: **one small PR, no visual change, no risk to any existing screen** — nothing is
translated, so nothing can regress. It does not extract the 1 422 strings; it stops the number
growing.

What it does **not** buy: the toggle still does nothing visible until step 1.

**My recommendation:** do step 0 whenever convenient — it is cheap and it is the only part of this
whose cost rises every week it is deferred. Steps 1–6 are post-launch.

## 5. What I am doing in the meantime

Without step 0 there is no way to write a genuinely translatable string, so the rule I am following
instead is the one that makes extraction mechanical later:

> **User-facing text is centralised per module, never inlined in logic.**

`BannerState::label()`, `PromotionState`, `TARGET_LABELS`, `STATUS`/`TONE` maps — every new screen
in wave 4D puts its vocabulary in one named place at the top of the file or in a domain class, so
step 0 can lift it by moving a map rather than by hunting through JSX. Eight modules already follow
this shape.

That is a mitigation, not a substitute. The honest position is the one at the top: the dashboard is
Arabic, 1 422 strings deep, and an English dashboard is a project we have costed rather than a
switch we have hidden.
