# UX and operational review — 2026-09-17

The dashboard as the data-entry team will actually use it: usability, performance under the real
catalogue, and how hard it is for a beginner to do damage. The first assessment against
production-scale data rather than 500 rows.

Bugs and usability findings are kept separate so they can be triaged separately. Nothing here was
fixed — the fix list is the developer's call. Method and the two withdrawn claims are at the end.


Catalogue under test: 7,713 products (7,087 imported Brand Fashion + 626 Watchizer), 110 variants,
2 storefronts, 9 real orders, 7,631 activity rows. Driven in-process through the real router,
middleware and controllers; every mutating probe inside a transaction that was rolled back.

## AREA A — PRODUCTS LIST AND PRODUCT FORM

### BUGS

**A-BUG-1 · The machine-translation flag clears itself on any save. HIGH.**
`ProductWriter::writeTranslations()` (app/Domain/Catalog/ProductWriter.php:346) writes
`is_machine => 0` on every pass through the door, whether or not the translation text changed.
That flag is the review queue for the 7,087 imported Arabic titles (`flag=machine_ar`). Measured:

- change ONLY `selling_price` on product 635 → flag 1→0, Arabic title provably identical.
- bulk deactivate 25 imported products, form never opened → 25 flags cleared, queue 7,087 → 7,061.
- the activity log records only `is_active`, so it cannot explain where the queue went.

The intent ("clear it when a human edits that translation") is right; the trigger is wrong.
Fix: clear only when the submitted text differs from the stored text — the comparison
`ActivityLog::diff()` already performs. ~1 h including a test.

**A-BUG-2 · A bulk action containing a stale id returns HTTP 500 after writing part of the batch. HIGH.**
`ProductController::bulk()` (line 437) loops with no transaction; `currentPayload()` throws for a
missing id. Measured: ids [real, 99999999, real] → 500, with the first product already deactivated
and the third untouched. The operator gets a crash page and cannot tell how much applied. A stale
tab or a product archived by a colleague is enough to trigger it.
Fix: wrap the loop in a transaction; skip unknown ids and report them. ~2 h.

**A-BUG-3 · A search of three or more `%` characters returns HTTP 500. LOW-MEDIUM.**
`ProductController::booleanTerm()` (line 870) strips `+ - * ~ < > ( ) " @` but not `%`, and filters
words by LENGTH only, so `%%%` reaches MariaDB as `+%%%*` → SQL 1064 "unexpected $end, expecting
FTS_TERM". Reproduced on both storefronts. `%%`, `...`, `###`, `؟؟؟` are all fine. Products list
only — the other screens use LIKE.
Fix: keep only words containing at least one letter or digit. ~30 min.

**A-BUG-4 · A category filter naming an unknown or foreign node silently returns the whole catalogue. MEDIUM.**
`?filters[category]=68` on storefront 1 (node 68 belongs to storefront 2) returns all 7,713 rows
with `meta.filters.category = null`. Same for `999999`, and for every out-of-whitelist filter value.
The operator asked for one category and is looking at everything — dangerous next to a bulk action
taken on "everything shown".
Fix: refuse an unresolvable filter value instead of dropping it. ~1 h.

**A-BUG-5 · A storefront-scoped grant does not contain a bulk write. MEDIUM.**
A data-entry user scoped to storefront 1 posted `deactivate` through the storefront-1 URL for a
product that lives only on storefront 2, and it succeeded (`is_active` 1→0). `is_active`, price,
titles and specs are SHARED columns, so scoping the URL scopes nothing but the URL. Reads are
correctly scoped (404 on the other storefront); writes to shared columns are not.
Fix: enforce the rule in the writer, or document the scope as placement-only. ~3 h.

### USABILITY

**A-UX-1 · Arabic search fails for ordinary Arabic typing. HIGH — the worst daily defect.**
Neither the index (`ProductIndexer`, body = raw title) nor the query normalises Arabic orthography:

| typed | found | actually in the catalogue |
|---|---|---|
| ساعه (ha for ta-marbuta) | 0 | 4,674 |
| حقيبه | 0 | 770 |
| نظاره | 0 | 1,239 |
| اسود (plain alef, as typed) | 1 | 506 |
| الرجالى (alef maqsura) | 0 | 13 |
| سـاعة (with tatweel) | 0 | 4,674 |
| سَاعة (with diacritics) | 4,674 | 4,674 — this one works |

An operator who types the word the ordinary way is told the product does not exist.
Fix: one normalisation function (ة→ه, أإآ→ا, ى→ي, ؤ/ئ, strip tatweel) applied in the indexer and in
the query, plus a re-index of 7,713 rows. ~4 h.

**A-UX-2 · Inner-word fragments find nothing.** `حفظ` inside `محفظة` → 0; `ilfi` inside `Hilfiger`
→ 0. Word-prefix index, as designed and documented — but it is what a junior tries second.
Mitigated by A-UX-1 plus a LIKE fallback when FULLTEXT returns nothing. ~2 h.

**A-UX-3 · The list loses the operator's place on every edit. HIGH for throughput.**
`edit_url` carries no list state, and the form's Cancel does
`router.get('/manage/storefronts/{id}/products')` — page 1, no filter, no search (Form.tsx:858).
Save redirects back to the edit page. So "fix one field on fifty products" is: filter, find, edit,
save, back, RE-TYPE the filter, re-find your position — fifty times.
Fix: carry the list query string into `edit_url` and back into Cancel; add "save and next". ~4 h.

**A-UX-4 · The Watchizer product screen shows 7,713 products for a 626-product shop.**
Storefront 1 lists the whole shared catalogue; only 626 are placed there, and `flag=unplaced`
returns 7,087. 92% of what that operator scrolls past is not their shop.
Fix: default to "on this storefront", with an explicit toggle for the whole catalogue. ~2 h.

**A-UX-5 · Badges that appear on nearly every row stop being signals.**
`flag=missing_data` matches 7,251 of 7,713 on storefront 1 (94%) and 3,441 on storefront 2;
`flag=machine_ar` matches 7,087.
Fix: a "needs attention" default view, with the sub-reasons counted separately. ~2 h.

**A-UX-6 · You cannot sort the list by name.** The sortable whitelist resolves `title` (and
`sp.is_visible`) back to `p.id`, so alphabetical browsing is impossible and the visibility column
shown on screen cannot be sorted. ~2 h.

**A-UX-7 · `import_ref` is not searchable.** `woo:38115` → 0 though `38115` → 1. The importer's own
`report.csv` names rows by `import_ref`, so the handover list cannot be pasted into the search box.
~30 min.

### PERFORMANCE — best of three warmed runs, in-process (no network cost included)

| scenario | time | note |
|---|---|---|
| default page, either storefront | 33-35 ms | 17 queries |
| deep page 309 (last) | 84 ms | index scan, no filesort |
| category branch (root, 4,692 rows) | 63 ms | the STRAIGHT_JOIN hint is working |
| Arabic search | 64 ms | FULLTEXT |
| 2-character search (LIKE fallback) | 78-82 ms | full scan by design |
| sort by any indexed column | 36-55 ms | |
| **`flag=missing_data`** | **174 ms**, 269 ms on page 100 | full scan + 4 materialised subqueries |
| worst combination | 213 ms | missing_data + search + sort |
| CSV export, 7,713 rows | 1.6-1.9 s, 2.1 MB | streamed, BOM present, 46 MB peak |

Bulk write cost is the real performance defect: deactivating 25 products issues **726 queries
(1.35 s)**; 100 products issues **2,919 queries (2.2 s)** — about 29 queries per product, because
each id is a full-replace product save. A 500-id bulk action would issue roughly 14,500.

### WHAT WORKS — tested and passed

- Every filter narrows the set and every returned row matches it (18 filters × 2 storefronts).
- Sort whitelist holds; unknown sorts fall back to `p.id`; no row appears on two pages.
- Hostile paging (`page=-3`, `per_page=1000`, `page=abc`) is clamped and never errors.
- Injection attempts in filters and search are inert.
- A full form round-trip on a hand-made watch leaves every column, spec, image, pivot and placement
  identical apart from image-sort renumbering and `published_at` being stamped.
- Pivots (features, genders, colours) are correctly guarded by `array_key_exists` and survive a bulk
  write that does not mention them.
- The activity log records bulk edits, one row per product, with from/to values.

## AREA B — THE MONEY PATHS: STOCK, ORDERS, CANCELLATION

### BUGS

**B-BUG-1 · Adjusting stock on a product that has sizes returns HTTP 500. MEDIUM-HIGH.**
`InventoryService` correctly refuses a product-level movement on a variant product (rule §2.5), but
it throws `InvalidArgumentException`, and `InventoryController::adjust()` catches only
`InsufficientStock` and `RuntimeException` (lines 431-441). `InvalidArgumentException` is not a
`RuntimeException`, so the refusal escapes as a Server Error page. Logged text:
"Product 5593 has variants, so its stock moves through a variant, never through the product.
Use StockTarget::variant()."
Two defects in one: the operator gets a crash instead of a field message, and the message is
English developer prose naming a PHP method. Brand Fashion sells clothing in sizes, so this is a
first-week event.
Fix: catch `InvalidArgumentException` and give it an Arabic operator sentence. ~1 h.

**B-BUG-2 · An invalid filter value silently returns the whole list — on every screen. MEDIUM.**
Measured: `orders?filters[storefront_id]=999` → 9 of 9; `ledger?filters[reason]=nonsense` → 5,795 of
5,795; `activity?filters[action]=nonsense` → 7,631 of 7,631; products as in A-BUG-4. The value is
dropped and `meta.filters` echoes null. This is the same family as the wave-4C dead-filter defect,
one layer further out: the filter works, the *rejection* does not.
Fix: one change in `TableQuery::resolvedFilters()` — refuse an unresolvable value. ~1 h.

**B-BUG-3 · The order provider and method filters can never accept a value. MEDIUM.**
`filterable` advertises `provider` and `method`, but their option lists are built from
`orders.paid_via_provider` / `paid_via_method`, which are written only by a SUCCEEDING payment.
No order in this database has either, so both option lists are empty (`"providers":[],"methods":[]`)
and any value passed is dropped, returning all 9 orders. AGENTS §4 records this exact shape as a
lesson already learned in 4C; the control survived.
Fix: build the option lists from the configured providers/methods, not from a success column. ~1 h.

### GUARDRAILS

**B-GUARD-1 · A stock adjustment of one million is accepted silently. MEDIUM.**
`quantity` validates `min:-1000000, max:1000000`. Typing 1000000 instead of 100 set a product to
1,000,005 units with a green "movement recorded" flash and no confirmation step. There is no
confirmation on ANY adjustment, of any size.
Fix: confirm above a threshold (say 100 units, or 10× current), stating the before and after. ~2 h.

**B-GUARD-2 · Order status changes and cancellations are not in the activity log. HIGH for handover.**
Verified by reading every writer: only `Roles`, `ProductWriter`, `InventoryService`,
`CategoryController`, `PaymentSettingsController`, `PlacementController` and `PromotionController`
call `ActivityLog::record()`. NOT audited: **order advance, order cancellation**, variant
create/update/delete, banners, shipping rates, all 11 lookup lists, unit merge/retire/restore,
storefront settings, media upload, media prune (deletes files), profile/locale.
A cancellation moves money and stock and is admin-only — the stock half leaves a ledger movement
with the actor, but who cancelled which order, when, and with what note is recorded nowhere the
activity screen can show.
Fix: `ActivityLog::record()` in `OrderFulfilment::advance()` and `::cancel()` first (~2 h), then the
other writers (~6 h).

**B-GUARD-3 · The activity log currently has no author on any row.**
All 7,631 rows have `user_id = NULL`: 7,611 product creations by the importer (CLI, no session) and
20 pre-handover grants. That is correct behaviour and not a defect, but it means the "who" column is
untested against real dashboard use, and the screen's most important filter (`user_id`) returns 0
for every user today.

### WHAT WORKS — and this is the strongest area of the system

The order state machine was attacked and held. Verified against the DATABASE after each call, not
against the HTTP status:

- Forward-only transitions enforced exactly: pending→shipped, →delivered, →completed, →cancelled and
  →bogus are all REFUSED from pending; every backwards move is refused (processing→pending,
  shipped→processing, completed→processing); a cancelled order cannot be re-opened.
- Cancel is refused from `delivered` and `completed` with a clear Arabic sentence telling the
  operator to treat it as a return, and refused on a second attempt ("already cancelled").
- **The cancel → re-open → cancel sequence that would mint stock is impossible**: the re-open is
  refused, so the restore cannot run twice. Stock verified before and after: e=3 → e=4, once.
- Cancellation restores stock through the ledger, records the operator's Arabic note on the
  movement, and reports the consequence with its number: "تم إلغاء الطلب وإرجاع المخزون (1 حركة في السجل)".
- Data-entry can advance fulfilment and adjust stock, and is refused cancellation — the §2.7 split
  holds at the database, not just in the menu.
- Stock adjust refuses: below-zero results, negative absolute values, a zero delta, a 256-character
  note, machinery reasons (`order`, `order_cancel`) typed by hand, a variant belonging to another
  product, a soft-deleted product, unknown ids. A no-op SET says so instead of writing a movement.
- Status, date-range and all ledger/activity filters narrow correctly and every returned row matches.

### MEASUREMENT LIMIT — stated rather than reported as a finding

Dashboard stock adjustments appeared to write no `integration_outbox` row. That is an artifact of my
method: `InventoryService` fires `StockChanged` inside `DB::afterCommit()`, and every probe here ran
in a transaction that was rolled back, so the listener never ran. The outbox seam is not shown to be
broken and is not claimed to be sound; it was not measurable this way.

## AREA C — PLACEMENT, VISIBILITY, CATEGORIES, SETTINGS

### BUGS

**C-BUG-1 · A storefront setting saved in the dashboard does not reach the shop for 10 minutes. MEDIUM-HIGH.**
`ResolveStorefront` caches the whole storefront row under `sf:code:{code}` for
`config('storefront.ttl.storefront')` = **600 s**, and `StorefrontController` performs no cache
invalidation of any kind. Measured end to end:

- prime the cache with a customer request → 200
- deactivate storefront 1 through the screen → database `is_active = 0`, cache still says 1
- customer request immediately after → **still 200**; a deactivated storefront keeps serving
- rename + currency EGP→USD + default locale ar→en → database updated, cache still serves the old
  name, currency and locale

So "deactivate storefront" cannot take a shop down promptly, a currency change is not live when the
screen says it is saved, and nothing on the screen mentions a delay.
Fix: forget `sf:code:{code}` (and bump the storefront cache version) in the update path — the
placement screen already does this kind of bump. ~1 h.

**C-BUG-2 · Deleting an empty leaf category silently does nothing. LOW-MEDIUM.**
`DELETE /manage/storefronts/1/categories/9` ("pilot" — no products, no children) returns 303,
leaves the row in place, and flashes neither an error nor a confirmation. Either the refusal has no
message or the delete is a no-op; from the operator's seat the button does nothing and says nothing.
Fix: whichever it is, say it. ~1 h.

### GUARDRAILS

**C-GUARD-1 · The guarded action is the small one; the bulk action has no confirmation. MEDIUM-HIGH.**
Hiding ONE product that sits in customers' carts opens a dialog naming the consequence — `in_carts`
is computed for exactly this (PlacementController:137). Hiding a whole page of products through the
bulk bar calls `router.post(...)` immediately (Placement/Index.tsx:338): **no confirmation, no cart
check, no count, no undo.** Measured: 200 products went from visible to hidden on the live
storefront in one request (7,579 → 7,379, 1,404 queries, 200 activity rows).
The blast radius is bounded — selection is per page and resets on paging, with the reasoning
written into DataTable.tsx:99 — so one click costs 25 products, or 100 if the operator raised the
page size. That is still a live shop losing a hundred products with no question asked.
Fix: route the bulk hide through the same `ConfirmAction`, stating the count and the cart total. ~2 h.

### WHAT WORKS

- **The visibility gates hold on BOTH paths.** A product with no image, and a product with no
  category on that storefront, stayed hidden after a single PUT *and* after a bulk show. §2.27 is
  enforced server-side, not just in the form.
- Deleting a category holding 384 products is refused; deleting a brand used by 3,006 products and a
  colour used by 351 products are refused.
- Pre-switch gates hold: creating a category is refused, and editing storefront 2's tree is refused.
- Unit retire/restore works and is reversible; merging a unit into itself is refused.
- The placement bulk endpoint skips ids with no placement row instead of crashing (unlike the
  products bulk endpoint, A-BUG-2) and writes one activity row per product, with the reasoning for
  per-product rows written into the code.

### CONFIRMED-BY-TEST, STILL A DESIGN QUESTION

**The lookup full-replace contract is reachable and destructive.** `PUT /manage/lookups/colors/{id}`
with `_complete=1` but no `hex` key **cleared the stored hex** (#111111 → empty) — the same damage
AGENTS §2.9.7 records from 2026-09-12. The `_complete` guard works (a payload without it is
refused), but the guard only proves the caller *meant* to send everything, never that it did.
This is documented and intended; it is listed here because the screens are now the only safe caller
and there is no test that the colour form always submits `hex`.

## AREA D — WHERE THE INTERFACE LIES OR CONFUSES

### The translation seam is in good shape — measured, not assumed

- 1,180 distinct keys are called (872 client, 436 server). The English dictionary holds 1,238.
- **Exactly 2 call sites have no English string**: `placement.slug_too_long` and
  `products.slug_taken` — both refusal messages, so an English operator meets Arabic at the one
  moment they are already stuck. ~15 min.
- Arabic stranded off the seam: **effectively none** (one language-name map, `ar: 'العربية'`, which
  is correct as-is). Arabic living in the components as the `t()` fallback is deliberate, documented
  in `lang/ar/manage.php`, and guarded by `LocaleSeamTest`.
- The English strings themselves are good ("Stock-count correction", "New delivery", "Out of stock
  in both"), not machine output.

### D-1 · The same words mean two different numbers on two screens. MEDIUM.
"مخزون منخفض" / "Low stock" is **4,946** on the home dashboard and **7,523** on the stock screen.
Home counts `is_active AND in_stock AND (e+m) <= threshold`; the stock screen counts
`(e+m) <= threshold` with no `in_stock`. The gap is exactly the 2,577 products that are out of stock
altogether. Both definitions are defensible; the label is identical.
Fix: one definition in one place, used by both. ~1 h.

### D-2 · The low-stock warning fires on 97.5% of the catalogue. MEDIUM — data, not code.
7,523 of 7,713 products are "low". The default `low_stock_threshold` is 5 and 7,577 products carry
the default, while imported stock is mostly 0-2 (1,857 in-scope rows arrived at ≤ 0). A flag that
is true of nearly everything is not a flag, and it is the headline number on the stock screen.
Fix: decide thresholds at import time, or make 0 mean "no threshold" and set 5 deliberately. ~2 h
plus a data pass.

### D-3 · Two home tiles always show the same number. LOW.
"المنتجات 7,713" and "منتجات مفعّلة 7,713" — nothing is inactive, so the second tile has never
differed from the first and reads as a duplicate or a bug. Its hint is the literal string
`is_active = 1`: a database expression shown to a data-entry operator on the first screen they open.
Fix: drop the tile or show it as a share of the first; replace the hint with a sentence. ~30 min.

### D-4 · English text is rendered in a right-to-left layout. MEDIUM for an English operator.
With `locale = en` the shared props still carry `dir = rtl` — `Preferences::TEXT_DIR` is a constant.
This is deliberate and recorded (i18n backlog step 1), and the reasoning is sound: the dashboard is
*written* in Arabic, so mirroring the layout around English labels while most literals are still
Arabic would be worse. The consequence is still that an English-reading operator gets English words
in a mirrored layout, which is not what "switch to English" implies.
Fix: tie `dir` to the chosen locale once English coverage is complete (it now is, at 99.8%). ~2 h
plus a visual pass on every screen.

### D-5 · "تحديد كل الصفوف" selects only the current page. LOW.
The checkbox says "select all rows"; it selects `allOnPage`. The behaviour is the safe one and the
reasoning is written into DataTable.tsx:99 — only the label overstates it.
Fix: "select the rows on this page". ~10 min.

### D-6 · Developer vocabulary reaching operator screens.
Examples confirmed in rendered props: `is_active = 1` as a hint on the home page; the uncaught
stock refusal "Use StockTarget::variant()" (B-BUG-1); "قبل ليلة التحويل" (before switch night) and
"القاعدة نفسها التي يستخدمها التحويل (config/transform.php)" on the product form — a config file
path shown to a data-entry operator.
Fix: these are individually one-line rewrites; the config-path one should go. ~1 h.

## WHAT WOULD ACTUALLY SAVE THEM TIME

Each is grounded in a task the team performs, with the cost measured.

1. **Keep the list state through an edit** (A-UX-3). Today: filter, open, save, Cancel → page 1
   unfiltered, retype the search, find your place. Measured at 4 requests and a re-typed query per
   product; on a 50-product correction pass that is 50 re-typings. Add "save and next". ~4 h.
2. **Normalise Arabic in search** (A-UX-1). The difference between finding 4,674 watches and
   finding none is one function. ~4 h.
3. **Default the product list to this storefront** (A-UX-4). The Watchizer operator scrolls past
   7,087 products that are not in their shop. ~2 h.
4. **Sort by name** (A-UX-6). ~2 h.
5. **A real "needs attention" queue.** The badges exist and are computed (`missing`, `machine_ar`,
   `placement`, `has_image`), but they fire on 94% of rows, so the operator cannot use them to pick
   work. One view, sub-counts per reason. ~2 h.
6. **Bulk edit of a field, not just a flag.** Bulk today is activate/deactivate/archive/restore and
   show/hide/feature. "Set brand", "set threshold", "set category" would each remove a
   50-product form-by-form pass. ~6 h.
7. **Make `import_ref` searchable** so the importer's own `report.csv` can be pasted in (A-UX-7).
   ~30 min.

The row itself is already information-rich — 28 fields including cover, badges and placement state —
so the list screen's bones are good; it is the movement between list and form that costs the time.

## GUARDRAILS — what should be impossible, confirmed, or recoverable

**Already impossible, and correctly so:** illegal order transitions; re-opening a cancelled order;
cancelling a delivered order; publishing a product with no image or no category (both paths);
deleting a category with products, a brand with products, a colour in use; a variant with history;
creating products/variants/categories/lookups before the switch; editing storefront 2's tree; a
data-entry user cancelling an order or reaching payments, users, promotions or storefronts; a
lookup write without `_complete`; stock below zero; a negative absolute quantity; machinery reasons
typed by hand.

**Should require confirmation and does not:**
- bulk hide/show on a live storefront (C-GUARD-1) — one click, up to 100 products, no question
- a stock adjustment of any size (B-GUARD-1) — 1,000,000 accepted with a success message
- bulk deactivate/archive from the products screen — same shape as the placement case

**Recoverable today:** products (archive/restore), units (retire/restore), categories
(deactivate), stock (a correcting movement, with the ledger keeping both).
**Not recoverable:** a bulk hide (no undo, and the previous per-product state is only in the
activity log); media prune (deletes files); a cleared lookup column.

**Does the activity log answer "who broke this and when"?** Partly. It answers it for products,
stock, categories, placement, payments, promotions and role grants — with before/after values, one
row per product even in bulk, credentials redacted, and a failure policy that never blocks the
business write. It does NOT answer it for **order status changes, order cancellations**, variants,
banners, shipping rates, lookups, units, storefront settings, media upload or media prune. Today
every one of its 7,631 rows has `user_id = NULL` (7,611 importer rows, 20 pre-handover test rows),
so the "who" column has never been exercised by a real dashboard session.

## HOW THIS WAS TESTED

In-process through the real router, middleware, controllers and Inertia — no browser and no network,
so timings are server-side only and exclude asset load and render. Every mutating probe ran inside a
transaction that was rolled back, with row counts compared before and after; the catalogue,
placements, orders, ledger, activity log and role grants are byte-identical to the state at the
start. Four principals were driven across all 76 dashboard routes: admin, unscoped data-entry,
data-entry scoped to storefront 2, and admin scoped to storefront 2.

**Two claims I withdrew after checking**, recorded because the method matters: dashboard stock
adjustments appear to write no ERP outbox row (they fire `afterCommit`, which a rolled-back probe
cannot observe), and 357 Arabic strings appeared to be off the translation seam (they are inside
multi-line `t()` calls the first scan could not see). Neither is a defect.
