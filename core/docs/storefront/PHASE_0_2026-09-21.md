The legacy **dashboard** is where nobody works. The legacy **storefront and its API are up**, and its
cart, checkout and `add_order` routes are the ones they have always been.

`RUNBOOK_ELEGANCEEG.md` §8 states the condition that makes the standalone database correct:

> *"the legacy Watchizer site is **stopped**. No new orders, no registrations, no stock movement,
> nothing writing to the legacy database."*

If `watchizereg.com` is taking orders, that condition is already false and §8's consequence list is
already running: two databases, no reconciliation tool, and `CORE_WRITE_SWITCH_COMPLETED=true` on
eleganceeg is a claim about something that has not happened.

**What is asserted here is only what was measured:** the machinery to place an order is answering.
Whether orders are being placed is a fact the developer holds, and it changes this plan's urgency,
not its shape:

- *Storefront live and selling* → the phase order below is a recovery schedule, not a roadmap.
- *Storefront live but no traffic* → normal pace, and the divergence is bounded.

**OPEN — developer to answer.**

### 2. Every push to `main` is a production deploy, including one that touches no storefront file

AGENTS §3: Hostinger rebuilds `Frontend-next` on **every** push to `main`, with `pnpm install`
**unfrozen**. Merging `wave-4d` into `main` — 8 commits of `core/` only — still rebuilds and
redeploys the live storefront and re-resolves its dependency tree.

And **`Frontend-next/.env.production` is committed** (intentionally: `NEXT_PUBLIC_*` is public client
config, AGENTS §3). So the API-base flip *is* a push to `main`. The flip and the deploy are the same
event and cannot be rehearsed separately on this host.

## 2. What v2 does not have, and what it costs

Sizes: **S** ≤ 1 day · **M** 2–4 days · **L** 1–2 weeks. All include tests, Pint, PHPStan level 10,
`tsc`.

### 2.1 The gate nobody has named yet

| # | Gap | Size | Why it is first |
|---|---|---|---|
| **G1** | **Customer auth in core** — token issuance; `register`, `login`, `logout`, `forgot-password`, `reset-password`, `auth/me`, `updateProfile`, `updatePassword`, `me/avatar`, Google `{provider}/redirect` + `/callback`, `verify-email` | **L** | see below |
| **G1a** | Re-open the `users` write door | **M** | `App\Models\User::booted()` refuses **every** save outside `DashboardAccounts::writing()`. That class's own docblock names the condition: the two-operation permission is *"void"* if another writer appears. Customer registration **is** that writer. A deliberate widening of the guard, not a bypass of it. The same docblock names `image` and `phone_number` as *"edited on the storefront"* — after the flip, core owns those writes too. |
| **G1b** | Google OAuth redirect URIs | **S** + client action | Registered against the legacy host in Google's console (`backend/app/Http/Controllers/Api/SocialAuthController.php`). Re-registering is developer-handled (AGENTS §3). |

**Why G1 gates everything.** Both databases carry a `users` table, and they diverge the moment either
side registers anyone. The compat layer proxies `login`/`register` to the legacy host — but
`LegacyJwt::userId()` checks the subject still exists in **core's** `users`. A customer who registers
on the legacy host after the flip therefore holds a valid token whose `sub` does not exist here:
**401 on every authenticated call, with no error anyone can read.** The storefront cannot be pointed
at the new database while auth is still proxied. It is one or the other.

### 2.4 DECISION OWED — guest-order → account linking

Every order in the legacy database is a guest order. That is how `compat:diff`'s `account:orders`
case reported IDENTICAL for two waves while comparing an empty list against an empty list
(AGENTS §3, 2026-09-13). So when auth moves into core:

- **(a)** A new account sees nothing it bought before. Simple, safe, and every customer's history
  reads as empty.
- **(b)** On registration, attach past guest orders matching the **verified** email. Needs a rule for
  phone-only orders and an answer for "two people, one shared email".
- **(c)** Attach on request, through the dashboard, by a human.

**Recommendation: (b) on verified email only, plus (c) for everything else.** This one is the
developer's: it decides what a customer sees the first time they sign into the new shop, and it is
not reversible once orders have been attached to the wrong person.

## 4. The order of work

Each phase leaves the site working; work can stop between any two.

**The constraint that sets the order, and it is not negotiable: catalogue reads and checkout writes
must hit the same database.** Product ids are preserved by the transform, so the two catalogues
*look* interchangeable — but a product the team created in the new dashboard has no legacy row, and a
stock decrement on the legacy host is invisible to the new ledger. Half a cutover is worse than none.

### Phase 1 — Customer auth in core — **L, ≈ 2 weeks**

Token issuance; the full auth surface (G1); the `users` write door widened deliberately (G1a); Google
redirect URIs re-registered (G1b). **Nothing deploys to the storefront.** The site is unchanged
throughout, which is what makes this the safe place to spend two weeks.

### Phase 2 — The cutover — **M, ≈ 4 days + the window** ← FIRST PHASE THAT CAN GO LIVE

- `Frontend-next/.env.production`: `NEXT_PUBLIC_API_BASE`, `LARAVEL_ORIGIN`, `NEXT_PUBLIC_ASSET_BASE`
  → the core host (see §5).
- On the core host: narrow the `/api` block (G2a), POST callback route (G2b), payment credentials
  (G2c/d/e), `COMPAT_LEGACY_BASE` stays pointed nowhere (`http://127.0.0.1:1`).
- Handle the four proxy-only features: wishlist (G6), ratings (G7), offers (G11), blogs (G9).

This is the switch-night design **(a-compat)** the compat layer was built and harness-proven for —
**0 storefront source files** beyond the auth calls repointed and those four features.

**What works:** the whole shop, on the new database, with the full Watchizer catalogue, the team's
dashboard edits live, promotions granting free items, the real ledger behind every sale.

**What does not:** no `/en/` URLs, no hreflang, no facet counts beyond what the client can compute,
no variants on the PDP, no money-reducing promotions, no blogs. And the catalogue still arrives as
one ~5 MB payload — **the flip fixes correctness, not speed.**

### Phase 3 — Native catalogue reads — **L** (study §3.6 waves a + b)

`meta`, paginated `products`, `products/{slug}`, server-side filtering and search. Retires
`transformProduct.js`, `catalogProjection.js`, `filterPredicate.js`, the bulk fetch and the 17 MB
hydration comment that documents why it exists. **Needs G3 (facets) and G4 (`?ids=`) first.** This is
the phase that pays the performance debt: 4.78 MB → the §5.5 budget of 45 KB.

### Phase 4 — Native cart, checkout, account — **M** (study §3.6 wave d)

Server-computed totals, which is what unlocks the money-reducing promotion types without weakening
`addOrder()`'s guard. Variants on the PDP land here.

### Phase 5 — Locale routing and SEO — **L** (study §3.6 waves c + e)

`/en/` prefix, hreflang, per-locale canonicals, the v2 sitemap adopted, **and G5 (redirects actually
served)** — which must land *with* this phase, not after, because this is when URLs move.

### Phase 6 — Content — **M**

Blogs, banners, the MT-Arabic decision, offers deleted.

**Risk profile.** The riskiest single moment is Phase 2's window. The riskiest *sustained* state is
the gap between today and Phase 2, because that is where two databases drift with nothing to merge
them back.

## 5. The deployment picture

### 5.1 Where the storefront calls the API — NOT `eleganceeg.com`

`App\Compat\CompatStorefront` resolves the storefront from the **request host**, matched against
`storefronts.domain` (`watchizereg.com`, `brandfashionegy.com`), exact or by sub-domain. Its own
docblock names the prerequisite:

> *"the two storefronts must answer on DISTINCT hosts. While both are served from one API host there
> is nothing in the request to tell them apart, the resolver falls through to the configured pin, and
> the identity is a guess with a sensible default."*

`eleganceeg.com` matches neither domain. Every cart, order, promotion evaluation and inventory
movement would fall through to `config('compat.storefront_id') = 1`. Correct today by luck — wrong
the day Brand Fashion launches, and wrong **silently**.

**Recommendation: `api.watchizereg.com`** — a sub-domain of the storefront's own domain, DNS-pointed
at the same Hostinger document root as `eleganceeg.com`. It resolves to Watchizer by the sub-domain
rule with no configuration, it leaves `eleganceeg.com` as the dashboard's address, and Brand Fashion
later takes `api.brandfashionegy.com` on the same host with no code change. Cost: one DNS record and
one certificate.

Note that the v2 routes themselves are host-blind — `/api/v2/{storefront}/…` carries the storefront in
the path and `ResolveStorefront` reads it from there. The host rule matters for the **compat** cart,
checkout and account paths, which Phase 2 depends on entirely.

### 5.2 CORS

`core/config/cors.php` already allows `https://watchizereg.com`, `https://www.watchizereg.com` and
`FRONTEND_URL`. Adding an API sub-domain of the same site changes nothing there. Two amendments worth
making in the same edit:

- `exposed_headers => ['X-Guest-Token']` (G10);
- drop `https://dash.watchizereg.com` from the origin list once nothing calls it.

### 5.3 The `/api` block

Runbook §7.2's own instruction: *"Remove this block on the day the v2 storefront is pointed at this
database — and not before."* Do not remove it — **narrow it.** Open exactly what Phase 2 needs and
keep `ProxyController`'s catch-all unreachable. The shape, to be written against the real route table
at Phase 2 rather than from memory:

```apache
RewriteCond %{REQUEST_URI} !^/api/(v2/|pay/|callback_payment|catalog/meta|all_product|all_product_image|all_product_rating|products/|show_shipping_city|add_to_cart|remove_from_cart|me/|cart/|add_order|add_address|login|register|auth/)
RewriteRule ^api(/|$) - [R=404,L]
```

**An allow-list, so the catch-all proxy stays unreachable.**
`COMPAT_LEGACY_BASE=http://127.0.0.1:1` is the belt; this is the braces; §7.2 asked for both.

### 5.4 How the storefront deploys once `main` is safe to push

Unchanged and unavoidable: push to `main` → Hostinger rebuilds `Frontend-next` (Node 22,
`pnpm install` **unfrozen**) → PM2 cluster, 2 instances, port 3000 (`ecosystem.config.js`). So:

1. Regenerate and commit `pnpm-lock.yaml` with any `package.json` change, always (AGENTS §3);
2. land `wave-4d` → `main` as its own deliberate push, verify the storefront after it, **then** start
   Phase 1;
3. the Phase 2 env flip is a `main` push and therefore a production event with no rehearsal available
   on this host. The rollback is the reverse commit, and it is fast because it is one file.
