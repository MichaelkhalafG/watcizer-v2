## §A — order 000092: charged, left cancelled

**Root cause (code, `CallbackPolicy::decide()` + `PaymentCallbackController::process()` as deployed):** a callback whose
outcome is `failed` on a `pending` order returned `ACT_CANCEL`: the order was set `cancelled` and
`InventoryService::releaseOrder(…, 'payment_failed')` returned its stock in the same transaction. Paymob's page stays
open after a declined attempt, and the shopper retried. The second callback (`success`, a NEW transaction id, so the
idempotency key did not match) found a `cancelled` order; `decide()` answered `ACT_RECORD_ONLY` + finding
`callback_on_terminal_order` ("a callback never moves an order out of a terminal state, and never re-reserves stock").
The attempt was recorded with `success = false`, `outcome = success`; the order stayed cancelled; the finding was
visible only on that order's page and in `php artisan payments:findings`. Nothing e-mailed anybody.

**Can the shopper retry on the same intention?** Paymob's public documentation does not say either way (Create
Intention and Unified Checkout pages read 2026-11-05: neither mentions retries or intention lifetime). The PAYLOAD
says yes: order 000092 has two transactions under one Paymob order — a decline, then transaction 566147894
`success = true` two minutes later — and core creates exactly one intention per order. Three more orders (000057,
000082, 000100) show the same second attempt, failed.

**Design built (RECOMMENDATION, taken as approved "straight to the fix"):**

1. **A decline does not cancel.** It is recorded as an attempt and the order keeps waiting, exactly like an order whose
   shopper is still typing. A later success pays it through the ordinary branch. If none comes,
   `orders:expire-unpaid` cancels it at the end of the existing window (`UNPAID_ORDER_EXPIRY_MINUTES`, 60) and returns
   the stock; the shopper's own next order supersedes it sooner (both existed already). The decline e-mail is not lost:
   the expiry sends the same recovery e-mail with the reason `declined` when the order saw a declined attempt.
2. **A success on a cancelled order brings it back when the stock is there** (`App\Domain\Orders\LatePayment`): the
   lines are reserved again through the ledger (`InventoryService::reinstateOrder()`, reason `order_reinstate`, all or
   nothing), the order becomes `processing` with `paid_via_*`, the customer and the shop get the order e-mails. Only an
   order cancelled FOR NON-PAYMENT (last release `payment_failed`) is brought back automatically — never one a person
   cancelled.
3. **When it cannot** (stock sold, product withdrawn, cancelled by a person): nothing is reserved, the finding is raised
   with the reason in its detail, and the shop is e-mailed at once.
4. **The decision is taken under the order row's lock**, on the status the order has at that moment. The twin delivery
   of one transaction (the provider's POST and the shopper's GET) is detected inside the lock.
5. **A decline on an already-cancelled order raises no finding** (no money moved): three of the four findings on
   production were this, and they buried the one that mattered.

**Alternative rejected:** keep cancelling on a decline and rely on reinstatement alone. It keeps the worst window open:
between the cancel and the retry the unit is back on sale, and with single-unit watches somebody else can buy it — the
paid customer then cannot be served. Holding the reservation until the window ends costs at most 60 minutes of one
unit per declined order, the same as an abandoned payment page costs today. Also rejected: a shorter "decline grace"
(for example 15 minutes) — the page can still succeed after it (intention lifetime is unmeasured), which only moves
the same case into net 2 more often.

**Stock through the ledger in every path:** new reasons `order_reinstate` (selling) and `reinstate_cancel` (the release
of a reinstated order: its first release reason is already spent on the same lines under the exactly-once index).
`isReleased()` is now "released and not reinstated since", so a later cancellation of a reinstated order returns its
units. No schema change (`reason` is `varchar(32)`).

**Alert:** every finding raised with the outcome `success` e-mails the storefront's order recipients
(`OrderMailer::paymentAlert()`, `emails/payment-alert-admin`, one per finding per recipient); the orders screen opens
with a red notice listing each one (`money_alerts`); the order's own page heads the findings panel with "the customer
was charged" and the sentence for the reason.

**Command:** `php artisan orders:reinstate-paid <number> [--storefront=] [--transaction=] [--apply]
[--cancelled-by-operator] [--no-customer-mail]` — dry run by default, same `LatePayment` code as the callback.

**Not touched, on purpose (RECOMMENDATION):** the wave-3 alias handler (`CheckoutCompatController::callbackPayment`)
shares the decision table, so a decline no longer cancels there either, but it does not reinstate — it keeps the
finding. It is dead wherever the contract is live (production).

## §1.3 — inventory:verify on production (read-only, for the developer)

```bash
cd ~/domains/eleganceeg.com/core
php artisan inventory:verify ; echo "exit: $?"
# green = the line "Ledger, variant columns, product aggregate and in_stock all agree." and exit 0.
# No --fix: without it the command only reads. (--json prints the same result for a script.)
```

Every other product in the state 25754 was in — a product WITH variant rows that still holds stock at product level, or
whose product-level movements do not sum to zero (invariant 3). Expect no rows:

```sql
SELECT p.id, p.wa_code, v.n AS variant_rows,
       p.stock_express, v.express AS variants_express, p.stock_market, v.market AS variants_market,
       COALESCE(m.express, 0) AS product_level_ledger_express, COALESCE(m.market, 0) AS product_level_ledger_market
FROM catalog_products p
JOIN (SELECT product_id, COUNT(*) n, SUM(stock_express) express, SUM(stock_market) market
        FROM catalog_product_variants GROUP BY product_id) v ON v.product_id = p.id
LEFT JOIN (SELECT product_id,
                  SUM(CASE WHEN bucket = 'express' THEN quantity_delta ELSE 0 END) express,
                  SUM(CASE WHEN bucket = 'market'  THEN quantity_delta ELSE 0 END) market
             FROM inventory_movements WHERE variant_id IS NULL GROUP BY product_id) m ON m.product_id = p.id
WHERE p.stock_express <> v.express OR p.stock_market <> v.market
   OR COALESCE(m.express, 0) <> 0 OR COALESCE(m.market, 0) <> 0
ORDER BY p.id;
```

Measured on `scratch_night_20261105` (57 variant products): 0 rows, and the query DOES find the state — with one variant
product's `stock_express` raised by 3 inside a rolled-back transaction it returned that product (27 against its
variants' 24). A product converted in the dashboard BEFORE Part 1 was deployed is the one way into this state (the units
stayed on the product; Part 1 moves them down), so any row it returns is such a product: move the units to the right
row from the Inventory screen, as was done for 25754.

**Run FIRST on production (read-only) — which pages were edited by a person:**

```sql
SELECT t.storefront_id, t.subject_type, t.subject_key, t.locale, t.updated_by, t.updated_at
FROM core_seo_texts t WHERE t.updated_by IS NOT NULL ORDER BY t.updated_at DESC;

SELECT a.id, a.created_at, a.user_id, a.user_name, a.storefront_id, a.subject_label
FROM core_activity_log a
WHERE a.subject_type = 'core_seo_texts' AND a.user_id IS NOT NULL AND a.created_at >= '2026-10-30'
ORDER BY a.id DESC;
```

Both empty = nobody edited a page text since the seed, and `--overwrite` rewrites all of them. Any row = that page is kept by the seeder; read it, then decide.

**A defect caught before it shipped (recorded because it would have been silent):** the first version of `SeoFacts` asked the app's own `/api/v2/…/products` over HTTP. It now calls the listing directly with the storefront bound as a request binds it; any failure is an exception.
