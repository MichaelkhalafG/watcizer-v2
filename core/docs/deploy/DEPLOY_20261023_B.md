```sql
-- 1. the order
SELECT id, order_number, status, payment_method, paid_via_provider, paid_via_method, total_price_for_order, created_at
FROM orders WHERE order_number = '<the number the confirmation showed>';
```

```sql
-- 2. the payment record (one row per settled delivery; Paymob calls back twice and the second is deduplicated)
SELECT id, provider, method, storefront_payment_method_id, pay_transaction_id, pay_order_id, amount_cents, success, outcome, created_at
FROM payment_statuses WHERE order_id = <the id> ORDER BY id;
```

```sql
-- 3. the units: reserved at placement, and NOT given back after a successful payment
SELECT reason, quantity_delta, quantity_after FROM inventory_movements WHERE reference_id = <the id> ORDER BY id;
```
**→ `order −n` only.** A `payment_failed` row here means the payment was recorded as failed and the order
cancelled: check `orders.status` and `payment_statuses.outcome` before touching anything.

What the shopper saw on the way, for the record (not the proof): `/checkout` → PLACE ORDER → Paymob's unified
checkout page (the URL begins `https://accept.paymob.com/unifiedcheckout/`) → the instrument → back on
`/order-confirmation?order=<number>&status=paid` (or `pending` for a kiosk reference). The account's **My
Orders** lists each one.

**If a payment fails or you abandon it on Paymob's page:** the order is `cancelled`, `payment_statuses` holds
`outcome failed`, the ledger holds `payment_failed +n`, and the shopper's cart is kept in the tab for the retry.
That is the same behaviour as before; it is listed so a cancelled row from a deliberate abandon is not read as
a defect.
