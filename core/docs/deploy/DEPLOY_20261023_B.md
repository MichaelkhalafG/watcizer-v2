through v2's `StorefrontCheckout::startPayment()` for the first time on storefront 1. It calls the **same**
`PaymentInitiator::initiate()` with the **same** arguments compat's path called (this storefront's contract,
the locale, the posted method, the order id and number, the amount, the billing) and on a failure cancels the
order and releases its stock exactly as compat did — but it has never been exercised in production on this
shop (Brand Fashion has never taken an order). §7 asks you to place one small card order yourself.

**No migration.** `php artisan migrate:status` on production must list **nothing pending**; if it lists
anything, **production is the authority — stop and say so**. The ledger is `core_migrations`.

## 5. If you have to roll back

**There is no migration, so there is nothing to roll back in the schema.**

* **Core:** restore the before-archive from §3.2 over `core/`, then `php artisan config:cache && php artisan
  route:cache`. Nothing in the data depends on the new core: the batched variant lookup answers the same
  question, the cache header is a number.
* **Storefronts:** `git revert` the four slice commits (and Part A's if you want it all back), push, let
  Hostinger rebuild. **A shopper's cart survives the rollback**: compat reads the same `carts` / `cart_items`
  rows v2 wrote. The one row compat cannot sell is a line with a `variant_id` — and no live product has
  variants today, so none can exist.
* **Do not** touch `orders`, `order_items` or `inventory_movements`: an order placed through v2 is an order.

**Hard-reload first.** A check straight after a build is unreliable until you do.

### Part A
- **Brand Fashion's hero**, desktop and phone: the two banners fill a 2.87-ratio band; nothing is cut to a
  square. (Measured fixed: 1377 × 480 and 358 × 160.)
- **Dark mode**: in Chrome, `chrome://flags` → "Auto Dark Mode for Web Contents" enabled → both sites stay
  light. (The media query never changed them; this is the thing that did.)
- **Home rails** (`/manage/storefronts/1/home-rails`): two reorders, one click straight after the other →
  **both stick**, and the live home shows the order within 60 s. A refused order shows a message above the
  list instead of silently redrawing.

### The cart, the checkout, the orders tab — Watchizer, as a shopper
1. Open a product page, add it → **the drawer opens** with the just-added card. **Reload the page → the
   drawer does NOT open** (it did, before today).
2. `/cart`: the line, its price **as the server prices it**, the governorate, CHECKOUT.
3. Place a **cash** order for a normal product → the confirmation shows the number, and it is **§4 step 6's
   number + 1**. The dashboard's orders list shows it; `order_items` carries the line; `inventory_movements`
   has its `−n` row.
4. Sign in → **My Orders** lists it (this shop's orders only; the same account's Brand Fashion orders — there
   are none — would show there, not here).
5. **A card order, small, yourself** — the first through v2's payment start on this shop. It must reach the
   Paymob page; coming back with `status=paid` lands on the confirmation. If the payment cannot start, the
   page says so, the order is cancelled and its stock released — check `orders.status = cancelled` and the
   `payment_failed` ledger row rather than trusting the sentence.
6. **A shopper who had a cart before the deploy**: open the site in the tab you left open, hard-reload → the
   cart page shows the server's lines at the server's price; if a price moved it says "Price updated — was …".
   Sign in with a guest cart in hand → it merges into the account's (quantities add), as before.

### What you CANNOT check live today

  The path is proved on the copy (order 000030, two variant lines, the ledger moving each variant's own
