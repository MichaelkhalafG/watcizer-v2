### B — the hydration error (both shops)

**What Michael saw** — "Minified React error #418 … args[]=HTML" — is React 19's "the server rendered HTML didn't match
the client" (Next 15's App Router runs React 19 whatever `package.json` pins). Two mechanisms, both reproduced on a
local production build and read in full on a dev build (`HANDOFF_20261107.md` §B has the component stacks):

1. **The menu.** The home's category row drew each category's fallback picture from the menu. The page seeded the
   menu through a `HydrationBoundary`, but the header's menu component had already created the menu query (empty,
   disabled) above it, and React Query fills an EXISTING query in an effect — which a server render never runs. So the
   server HTML showed a letter for every category without a picture of its own, while the browser's first render, on
   any page load after the first of a visit, had the sessionStorage copy (`initialData`) and drew the picture: two
   different trees — #418, on the home, for every returning visitor. The Hot Deals and Flash Sale pages had the same
   fault in their "nothing running" state (the "shop by category" list).
   **Fix:** the home hands the menu to the row as a PROP from its own server render (same on both sides by
   construction) and seeds the query cache after mount; the campaign pages hand their idle categories the same way
   (`idleMenu`, a few hundred bytes); `useMenu` no longer feeds a storage copy into a first render — it enters the cache
   in an effect, still long before any hover.
2. **Time.** Every countdown and every "is the campaign live" took `Date.now()` in its first render. The HTML is held
   for minutes (ISR, the server's 30-second hold), so a campaign that ENDED in between was in the HTML and gone from the
   browser's first render, and at a day boundary the countdown changed SHAPE (`3d` prefix, the day box) — neither is
   covered by `suppressHydrationWarning`. **Fix:** the campaigns answer's own second (`now`, core's clock, carried in the
   same HTML) is the first render's "now" on both sides; the device's clock takes over right after mount. No
   `suppressHydrationWarning` is left on the countdowns.

Proof: §7.1. Nothing to do on the server.

## 8. How a wheel code behaves with Black1000 and the live campaigns (not changed; reported)

- **One code at a time.** The cart and the checkout have ONE code field, so a shopper holds either a wheel code or
  Black1000, never both. The engine's stacking rule is untouched: a rule combines only when marked `stackable`, and
  neither the wheel's prize rules nor Black1000 is; the best single discount wins by `priority DESC, discount DESC`
  (all at priority 0). A wheel code typed while an automatic rule gives more → `not_best` ("a better offer already
  applies"), the automatic rule applies (`WheelTest › does not stack…`).
- **Hot Deals / Flash Sale** are the products' own sale prices, not promotion rules — and, since 2026-11-10, may carry a
  CAMPAIGN PRICE per product (§2 D), which is a price too: what a shopper pays with Black1000, a wheel code or a
  free-shipping code on top is measured in HANDOFF §DAY5.
- (2026-11-08) Hot Deals / Flash Sale without a campaign price: A wheel code is priced on the
  price CHARGED — the sale price — because the prize rules carry `include_sale_items = true` (the brief's "every spin
  wins"; the cap of EGP 1,500 still applies). So 10 % off a Flash Sale watch is 10 % of its sale price. The campaign's
  progress bar and countdown are unaffected.
- **Free shipping** is the delivery the cart is charged; above the free-shipping threshold it gives nothing extra
  (the threshold is decided before promotions, as before).
