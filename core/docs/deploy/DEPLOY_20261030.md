## 5. Rollback

- **Storefronts:** revert the storefront commits and push; Hostinger rebuilds. An old storefront against the new core
  is safe (free shipping §6 is about the opposite order). The security commit is independent of the rest: revert it
  alone only if the upgrade itself misbehaves (it brings the advisories back).
- **Core:** restore the before-archive, `config:cache` + `route:cache`. The migrations are forward-only in
  production; if the release is withdrawn, the hand-written SQL, newest first: `SEO_ITEM5` (below),
  `ACTIVITY_LOG_20261030.md` §5, `BULK_PRICE_20261030.md` §5, `PROMOTIONS_20261030.md` §7, `FREE_SHIPPING_20261029.md`
  §3. Page texts: `DROP TABLE core_seo_texts; DELETE FROM migrations WHERE migration = '2026_10_30_000003_seo_texts';`
  (after the code; nothing else reads the table).
- **Never** touch `orders`, `order_items`, `promotion_order_discounts`, `promotion_redemptions` or
  `inventory_movements` in a rollback: an order placed is an order.

   a second run says "Already there").

   empty**, **Active on**, save. The client switches it off (Active off) when the offer ends.
4. **Test order** on watchizereg.com (hard reload): a watch of one of the six brands, in stock → cart → code
   `Black1000` → "Code applied Black1000" and a discount line of −1,000 EGP per watch → checkout, cash on delivery,
   place it. Expected: the confirmation total = price − 1,000 + delivery. On the server:

   ```sql
   SELECT r.order_id, r.code, r.amount, r.created_at FROM promotion_redemptions r ORDER BY r.id DESC LIMIT 1;
   -- → your order, code Black1000, amount 1000.00 × the watches
   SELECT d.order_id, d.code FROM promotion_order_discounts d WHERE d.order_id = <that order>;
   -- → one row, code Black1000
   ```

   Then cancel the test order on the dashboard as for earlier test orders (`DEPLOY_20261023_B.md` §7).
5. A watch of another brand (or a non-watch) with the code: the cart says the code does not include those items, and
