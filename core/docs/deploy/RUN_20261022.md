### The dashboard finding that reached you as garbled Arabic

It was this, in English: the "today against the same weekday" label printed the **number of weeks** it was
averaging, through a string that read `:weeks أسابيع`. Arabic takes a different plural form for 1, for 2, for
3–10 and for 11+, so with one week of history it rendered **`1 أسابيع`** — wrong in the way "1 weeks" is wrong
in English. The count earned nothing in that sentence, so I removed it rather than build a plural system: the
label now reads "against the same day in earlier weeks" / "مقارنة بنفس اليوم في الأسابيع السابقة".

### Slice 1, first half — the listing reads v2 (done, gate green)

#### What it WAS, and why the estimate was wrong

The inventory put slice 1 at 10–14 h on the premise that Brand Fashion had already run this exact path since
2026-10-17, so the adapter existed and was proven. The adapter did exist. Reusing it as it stood would have
**silently removed two working filters from a live watch shop**, and I measured that before touching anything:

| Watchizer's sidebar had | v2 had | what the move would have done |
|---|---|---|
| **Movement** — 3 values, 652 products | nothing | the section would have drawn no items and vanished |
| **Watch Shape** — 6 values, 572 products | nothing | same |
| **Sub Type**, several ticked at once | `category` took ONE path | multi-select would have become pick-one |

You agreed to build parity rather than ship the loss. So slice 1 grew a core half the estimate did not contain.
**Revised: 18–22 h**, of which roughly 6–8 h is that core work. The frontend half came in near the estimate.

#### What was built in core

* `ProductListing::WATCH_SPEC_FACETS` — `movement`, `shape` and `display_type`, counted from
  `catalog_product_watch_specs` and filterable by id list, each computed with every filter applied except its
  own (compat's rule, unchanged). Display Type was added for symmetry, as you asked, so the three watch
  attributes are one mechanism rather than two plus an exception.
* `category` now accepts a **comma-separated list of paths** and answers their **union**, which is what a
  multi-select sub-type section has always meant on Watchizer. One path behaves exactly as it always has —
  same total, same `meta.category.path`, same `position` default sort — and that is what makes it safe to put
  under a live listing. An unknown path still 404s the **whole** request, so a filter the server did not
  understand can never look like a filter that matched nothing.
* `V2\ProductController` validates the three new keys. Worth recording because it cost an hour: the controller
  drops any key it does not validate, so `?movement=1` returned the whole catalogue and looked like a broken
  filter when the filter was never reaching `ProductListing` at all.
* Tests: `ListingWatchSpecFiltersTest` (new, 5 tests) pins the promise rather than the plumbing — a facet names
  only values the result contains, each filter agrees with a count taken straight from the table, an unknown id
  matches nothing, several paths are a union, one path is unchanged, and a bad path refuses the request.
  `ListingFacetsTest` grew to nine sections.

#### What it costs: queries and time, compat against v2

Both dispatched through the real HTTP kernel (so middleware, storefront resolution and serialisation are
counted), on the scratch copy of production, caches warm — the state a live shop is in. One warm-up, then five
runs; the median is reported.

| Request | queries | median | products |
|---|---|---|---|
| compat `catalog/listing`, whole catalogue | 1 | 31 ms | 1,014 |
| **v2 `products`, whole catalogue** | **6** | **19 ms** | 1,014 |
| compat `catalog/listing`, one sub-type | 1 | 27 ms | 21 |
| **v2 `products`, one sub-type** | **6** | **18 ms** | 21 |
| **v2 `products`, THREE sub-types** | **6** | **18 ms** | 59 |
| compat `catalog/listing`, movement filter | 1 | 32 ms | 534 |
| **v2 `products`, movement filter** | **6** | **19 ms** | 534 |

**Budget: 7 queries and 250 ms warm.** v2 is at **6 queries** — the existing `V2\QueryBudgetTest` already
asserts ≤ 7, and the three new watch-spec facets and the multi-path category did **not** add a query, because
the facets are built as one grouped sub-select each inside the same pass. It is at **19 ms**, comfortably
inside the budget.

The query counts are not comparable as a quality measure and should not be read as a regression: **compat does
one query because it loads a cached snapshot of the whole catalogue and filters it in PHP**; v2 does six
because it filters and counts in SQL. That is why v2 is the faster of the two despite six times the queries,
and why its cost does not grow with the number of filters — the three-sub-type union costs exactly what one
sub-type costs. compat's does not grow either, but it pays the whole catalogue on every request regardless.

Cross-check that the move is faithful on the single-path case: compat `subTypes=1` and v2
`category=watches/diver` both report **21** products, and compat `movements=1` and v2 `movement=1` both report
**534**.

The product page and cart numbers are not in this table because neither has moved yet: the product page is the
second half of slice 1, and the cart is slice 3. They will be measured against the same budget when they do.

#### What the shopper will actually see change

Three of these are real behaviour changes on a live shop, and none is cosmetic. The first two are v2's own
design, which Brand Fashion has run since 2026-10-17; this wave is when they reach Watchizer.

1. **The two colour sections become one.** compat counted a dial colour and a band colour separately — 18
   values each. v2 counts a colour in **any** role: 20 values, which is exactly the union of the two compat
   sets (measured: no value gained or lost). So "Dial colour" is renamed **Colour / اللون** and **Band colour
   is gone**. A shopper who wants a brown strap now ticks Colour → Brown and gets brown anywhere, dials
   included.
2. **Material counts a material in either role.** compat counted the **band** material only
   (`CompatListing.php:742`). v2 counts band **or** case. Steel goes from 343 products to **661**, leather from
   139 to 140, and one material (id 5) appears that compat never listed. The filter changed with the facet, so
   the count and the result still agree — but the *meaning* of the section is wider than it was. If you want
   Material to go back to meaning the strap, say so: it is a one-line change in `ProductListing`. I have left
   it matching v2 and Brand Fashion rather than making Watchizer the exception.
3. **The price slider finally has real ends.** compat serves **no price facet at all**, which is why the slider
   ran to a meaningless ceiling. v2 serves `{min: 300, max: 12500}` for the whole catalogue and recomputes it
   per result — 850–9,400 on fashion, 300–2,200 on electronics, 2,040–12,500 on watches. The defensive
   fallback for a payload with no facet block at all came down from 10,000,000 to 1,000,000 EGP, and the
   sentinel that means "no upper cap" is now a named constant instead of `99999999` typed in four places.

#### The new general rule: a section that cannot narrow anything is not drawn

You asked for it as a rule, not an exception, and it is one: `FilterSection` returns nothing below **2**
options. One option is not a filter — ticking it returns the same products, for the price of a heading, a row
and a decision. A section whose second value appears later starts drawing again on its own, with no code change.

What it hides **today**, measured in both apps:

| Shop and page | hidden by the rule |
|---|---|
| Watchizer, whole catalogue and any watch result | **Display Type** — one value (Analog, 637 products) |
| Watchizer, any narrow result | whatever has collapsed to one option |
| Brand Fashion, `/category/electronics` (72 products) | **Brand** — one value |
| Brand Fashion, `/category/fashion` (278 products) | nothing *extra* — the watch sections were already empty |

Nothing is hidden that a shopper could have used. A zero-count value never drew in the first place (`build()`
has always filtered `count > 0`), so the rule's whole effect is the exactly-one case. On Watchizer the net
effect is nil: Display Type is a section this wave **added**, and the rule hides it again on today's data.

#### Brand Fashion's sidebar after the change — measured in Brand Fashion's own app

Brand Fashion renders Watchizer's `ListingClient` and `SideBar` with its own skin sheet, so the core change
reaches it. It sells watches out of the same shared catalogue, and the facets follow **what the result set
actually contains**, not what the schema could hold. Read off its running listing at 1440 px:

| Brand Fashion page | products | sections drawn |
|---|---|---|
| `/listing` | 1,014 | Brand, Sale, Price, Sub Type, Gender, Dial Color, Material, **Watch Shape**, **Movement** |
| `/category/watches` | 664 | the same nine |
| `/category/fashion` | 278 | Brand, Sale, Price, Sub Type, Gender, Dial Color, Material |
| `/category/electronics` | 72 | Sale, Price, Sub Type |

So Brand Fashion **gains** Watch Shape and Movement on watch results — it had neither before, because v2 served
no such facet and every count was zero — and loses nothing. The concern that a fashion shop would sprout watch
filters resolves itself: **0 of its 278 fashion products and 0 of its 72 electronics products carry any watch
spec**, so those facets come back empty and the rule hides them.

One thing I did **not** change: Brand Fashion's colour section is still titled "Dial Color" although v2 has
counted a colour in any role there since 2026-10-17. That mislabel predates this wave and the two `SideBar.jsx`
files are a recorded divergence, so I left Brand Fashion's presentation alone rather than widen the diff. It is
a one-word fix whenever you want it.
