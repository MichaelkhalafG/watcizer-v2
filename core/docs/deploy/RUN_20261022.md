### The dashboard finding that reached you as garbled Arabic

It was this, in English: the "today against the same weekday" label printed the **number of weeks** it was
averaging, through a string that read `:weeks أسابيع`. Arabic takes a different plural form for 1, for 2, for
3–10 and for 11+, so with one week of history it rendered **`1 أسابيع`** — wrong in the way "1 weeks" is wrong
in English. The count earned nothing in that sentence, so I removed it rather than build a plural system: the
label now reads "against the same day in earlier weeks" / "مقارنة بنفس اليوم في الأسابيع السابقة".

#### What was built in core

* `ProductListing::WATCH_SPEC_FACETS` — `movement`, `shape` and `display_type`, counted from

  same total, same `meta.category.path`, same `position` default sort — and that is what makes it safe to put
  under a live listing. An unknown path still 404s the **whole** request, so a filter the server did not
  understand can never look like a filter that matched nothing.
* `V2\ProductController` validates the three new keys. Worth recording because it cost an hour: the controller
  drops any key it does not validate, so `?movement=1` returned the whole catalogue and looked like a broken
  filter when the filter was never reaching `ProductListing` at all.
* Tests: `ListingWatchSpecFiltersTest` (new, 5 tests) pins the promise rather than the plumbing — a facet names
  only values the result contains, each filter agrees with a count taken straight from the table, an unknown id
  matches nothing, several paths are a union, one path is unchanged, and a bad path refuses the request.
  `ListingFacetsTest` grew to nine sections.

#### What it costs: queries and time, compat against v2

Both dispatched through the real HTTP kernel (so middleware, storefront resolution and serialisation are
counted), on the scratch copy of production, caches warm — the state a live shop is in. One warm-up, then five
runs; the median is reported.

| Request | queries | median | products |
|---|---|---|---|
| compat `catalog/listing`, whole catalogue | 1 | 31 ms | 1,014 |
| **v2 `products`, whole catalogue** | **6** | **19 ms** | 1,014 |
| compat `catalog/listing`, one sub-type | 1 | 27 ms | 21 |
| **v2 `products`, one sub-type** | **6** | **18 ms** | 21 |
| **v2 `products`, THREE sub-types** | **6** | **18 ms** | 59 |
| compat `catalog/listing`, movement filter | 1 | 32 ms | 534 |
| **v2 `products`, movement filter** | **6** | **19 ms** | 534 |

**Budget: 7 queries and 250 ms warm.** v2 is at **6 queries** — the existing `V2\QueryBudgetTest` already
asserts ≤ 7, and the three new watch-spec facets and the multi-path category did **not** add a query, because
the facets are built as one grouped sub-select each inside the same pass. It is at **19 ms**, comfortably
inside the budget.

The query counts are not comparable as a quality measure and should not be read as a regression: **compat does
one query because it loads a cached snapshot of the whole catalogue and filters it in PHP**; v2 does six
because it filters and counts in SQL. That is why v2 is the faster of the two despite six times the queries,
and why its cost does not grow with the number of filters — the three-sub-type union costs exactly what one
sub-type costs. compat's does not grow either, but it pays the whole catalogue on every request regardless.

Cross-check that the move is faithful on the single-path case: compat `subTypes=1` and v2
`category=watches/diver` both report **21** products, and compat `movements=1` and v2 `movement=1` both report
**534**.

The product page and cart numbers are not in this table because neither has moved yet: the product page is the
second half of slice 1, and the cart is slice 3. They will be measured against the same budget when they do.

#### The new general rule: a section that cannot narrow anything is not drawn

You asked for it as a rule, not an exception, and it is one: `FilterSection` returns nothing below **2**
options. One option is not a filter — ticking it returns the same products, for the price of a heading, a row
and a decision. A section whose second value appears later starts drawing again on its own, with no code change.

What it hides **today**, measured in both apps:

| Brand Fashion, `/category/fashion` (278 products) | nothing *extra* — the watch sections were already empty |

Nothing is hidden that a shopper could have used. A zero-count value never drew in the first place (`build()`
has always filtered `count > 0`), so the rule's whole effect is the exactly-one case. On Watchizer the net
effect is nil: Display Type is a section this wave **added**, and the rule hides it again on today's data.

### Slice 1, second half — the product page: the gap report FIRST (2026-10-23)

The rule I wrote for myself after the two overruns — *before moving a screen to v2, diff what v2 serves against
what that screen's controls already do on compat* — applied here before a line was changed. It found three real
gaps and cleared one I had wrongly suspected.

**First correction to the plan: Brand Fashion's product PAGE is not the model.** Only its `serverV2.js` is. Its
`app/(main)/product/[slug]/page.jsx` renders `BfProductPage`, not the shared `ProductDetailClient`, and it
**deliberately dropped** what Watchizer cannot drop — its own comment says so: "the legacy raw-title redirect of
the copied page is not carried — recorded". Brand Fashion is not indexed; Watchizer is, and is live.

**Second: the product page is TWO reads, not one.** The server fetches `catalog/product` for SEO and the
above-the-fold card, and then `ProductDetailClient` fetches the FULL record itself from the browser —
`products/{id}`, or `products/by-name/{param}` for a legacy URL (lines 173–198). Moving only the server read
would have moved half the page.

#### What v2 serves against what the screen already does

| the screen, on compat | v2 | verdict |
|---|---|---|
| server: `catalog/product?slug=` → cards, meta, images, ratings | `products/{slug}` → product + related + locale, resolved and localized | **v2 is a superset** |
| client: `products/{id}` → the full flat record for specs and gallery | already inside `products/{slug}` | **v2 removes a round trip** |
| watch spec rows, built in the browser from ~20 flat columns and their `_ar` siblings | `specs[]` pre-built: `{key, label:{en,ar}, value, unit}` | **v2 is better** — labels and units come from core |
| resolve by **numeric id**: `catalog/product?slug=437` → **200** | `products/437` → **404** | **GAP 1** — v2 is slug-only |
| resolve by **legacy raw title**: `products/by-name/COACH Women's Signature Canvas Medium Corner Zip Wallet CW786` → **200** | no endpoint at all | **GAP 2** — no v2 equivalent |
| family extras on the 20 products that have them | served, but see below | **GAP 3** — labels, units and booleans |
| `catalog/related` rail | `products/{slug}/related` → 200, and `related` is embedded in the detail payload | present |
| the reviews list and posting a review (`all_product_rating`, `add_product_rating`) | nothing | **stays on compat** — slice 6, out of scope by the brief |

**A gap I suspected and disproved, because I measured it.** The first non-watch product I checked came back
from v2 with an empty `specs[]`, which looked like the watch-filter mistake all over again — v2 not serving what
the screen shows. It was not: that product has no extras on compat either. `ProductDetail::familySpecs()` does
read `catalog_products.specs`, and **all 20** products that carry legacy `extra_attributes` have those keys
present in the clean-core column, identical, nothing lost in the migration. A wallet comes back from v2 with
all six of its rows. Had I reported from the first product I would have invented a data gap that does not exist.

**GAP 3, the real one, is the labels.** `familySpecs()` builds a row's label as
`ucfirst(str_replace('_', ' ', $key))` **for both locales**, and passes the stored value straight through. The
browser has a curated `EXTRA_LABELS` map instead, with proper bilingual labels, units, and booleans rendered as
Yes/No. On the 20 affected products (19 fashion, 1 watch), moving as-is would have printed:

| today, from the browser's map | from v2 as it stands |
|---|---|
| Width — 13 cm | Width cm — 13 |
| Card Slots — 8 | Wallet card slots — 8 |
| Coin Pocket — Yes | Coin pocket — 1 |
| العرض — 13 cm (Arabic) | Width cm — 13 (English, on the Arabic page) |

Same class of defect as the watch filters: v2 not yet doing what the screen already does. So core grows it —
the curated labels, units and boolean rendering move **into `familySpecs()`**, where they serve both
storefronts and anything else that reads v2, instead of staying private to one component.

#### The decisions taken, not blocked on

**D1 — the product page reads v2 first and keeps compat as its fallback chain.** v2 `products/{slug}`, and when
v2 does not know the slug: compat's slug lookup, then compat's by-name, then the brand-page 308, then 404 —
exactly the ladder that exists today. *Why:* gaps 1 and 2 are live indexed URLs on a shop Google crawls. *The
alternative* — move cleanly and let legacy URLs 404 — would drop real products out of the index to make one
file tidier. *Cost:* the product page keeps a compat dependency, listed below, and it is only ever reached when
v2 says no.

**D2 — `/products/[id]` stays entirely on compat.** It is a redirect-only route (numeric id → canonical 308)
and v2 has no id lookup. The brief says to leave an endpoint with no v2 equivalent on compat and list it rather
than invent one, so that is what this does.

**D3 — the browser's full-record fetch is removed.** The server already holds everything v2's detail payload
carries, so it hands it to the component instead of the component asking core a second time. The product page
goes from two upstream reads to one. This is the measurable win of the half-slice, and it is only possible
because v2's payload is the superset the table above shows.

**D4 — the curated family-spec labels move into core** (gap 3), not into the adapter. A label that belongs to a
field belongs with the field.

**D5 — reviews stay on compat.** `all_product_rating` and `add_product_rating` have no v2 equivalent and
ratings are explicitly slice 6. Listed, not built.

#### Still on compat after this half-slice, deliberately

`products/by-name/{title}` (the legacy raw-title fallback, D1) · `catalog/product` (the same fallback, and the
`/products/[id]` redirect, D2) · `all_product_rating` and `add_product_rating` (reviews, D5) · `catalog/meta`
and `catalog/nav` (the brand-redirect lookup and the menu — slice 2, deliberately out) · the offer pages, which
render the same component on compat and are untouched.

#### What was built, and the two gaps the rule found AFTER the first three

The gap report above was written before any code changed. Two more turned up while building, both the same
class, and one of the two I had wrongly called a gap earlier — recorded in the order they happened because
the order is the point.

**GAP 4, suspected and DISPROVED.** v2's related endpoint returned 200 for `?exclude=`, and `exclude` appeared
nowhere in `V2/ProductController` or `ProductDetail`, which looked exactly like the unvalidated-key trap that
made the movement filter match everything. It is not: the rails have their own `V2/RelatedController`, and it
reads `exclude`, applies it to both rails, and runs `CompatRelated` itself — the developer's scoring of
2026-09-29, the same class, not a reimplementation. Second time the rule stopped me inventing a gap; both
times the cure was reading the code rather than the grep.

**GAP 5, real: a flag was served as a raw boolean.** `interchangeable_dial`, `interchangeable_strap` and
`watch_box` came out of v2 as `true`, and Watchizer's page printed the literal "true" the moment it read the
rows from core instead of building them itself. Brand Fashion never showed it because `BfProductPage` carries
its own `typeof v === 'boolean'` branch — the same private-knowledge problem as the family-spec labels, in a
different component. Fixed in core, where the field is: `$flag()` now serves `{en: 'Yes', ar: 'نعم'}` through
the same helper the family specs use, Brand Fashion's object branch handles it unchanged, and neither
storefront needs to know. The adapter keeps a boolean branch anyway, so a rolled-back core still prints a word.

**GAP 6, real, and the largest of the six: five spec rows are not in `specs[]` at all.** Dial colour, Band
colour, Country, Stone and Warranty. Core serves every one of them — the colours under `attributes.colors` by
role, the other three as their own fields — it just does not file them under specs, because Brand Fashion
renders colours as swatches and would otherwise print them twice. Reading `specs[]` alone would therefore have
dropped them from Watchizer's table:

| row | products that would have lost it |
|---|---|
| Dial / Band colour | **936 of 1,014** visible products |
| Warranty | **523** |
| Stone, Country | the rest of the catalogue's own rows |

So the table's COMPOSITION is done in the storefront adapter, over data core already sends, rather than in
core: it is Watchizer's presentation choice, and Brand Fashion has made a different one from the same payload.
The five rows land at the END of the table instead of interleaved with their materials as they were on compat —
same rows, same values, five of them further down, and a one-line reorder if that is wrong.

* **`src/lib/v2Product.js`** — NEW, a twin. v2's detail payload → the compat cards shape every consumer here

#### Running total: six gaps in three screens

The rule has now been applied to the listing and the product page and has found six gaps, four real:

| # | gap | real? |
|---|---|---|
| 1 | movement and shape filters missing from v2 | yes — built in core |
| 2 | v2's category took one path, the sidebar is multi-select | yes — built in core |
| 3 | family spec labels machine-humanized, booleans raw | yes — built in core |
| 4 | v2 related ignoring `exclude` | **no** — it honours it |
| 5 | watch flags served as raw booleans | yes — built in core |
| 6 | five spec rows absent from `specs[]` | yes — composed in the adapter |
| — | non-watch `specs[]` empty (feared a data gap) | **no** — the migration carried it |

Two of seven suspicions were wrong, and both would have become a false claim in a report if I had stopped at
the grep. The pattern in the four real ones is identical every time: **v2 is a newer API that was written
against a specification, and Watchizer's screens are older than that specification and do more.** For the cart
and the checkout, where the same mistake would cost money rather than a filter, the diff goes first again.
