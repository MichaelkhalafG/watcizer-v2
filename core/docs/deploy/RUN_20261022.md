### The dashboard finding that reached you as garbled Arabic

It was this, in English: the "today against the same weekday" label printed the **number of weeks** it was
averaging, through a string that read `:weeks أسابيع`. Arabic takes a different plural form for 1, for 2, for
3–10 and for 11+, so with one week of history it rendered **`1 أسابيع`** — wrong in the way "1 weeks" is wrong
in English. The count earned nothing in that sentence, so I removed it rather than build a plural system: the
label now reads "against the same day in earlier weeks" / "مقارنة بنفس اليوم في الأسابيع السابقة".

#### What was built in core

* `ProductListing::WATCH_SPEC_FACETS` — `movement`, `shape` and `display_type`, counted from

  understand can never look like a filter that matched nothing.

  drops any key it does not validate, so `?movement=1` returned the whole catalogue and looked like a broken
  filter when the filter was never reaching `ProductListing` at all.
* Tests: `ListingWatchSpecFiltersTest` (new, 5 tests) pins the promise rather than the plumbing — a facet names
  only values the result contains, each filter agrees with a count taken straight from the table, an unknown id
  matches nothing, several paths are a union, one path is unchanged, and a bad path refuses the request.

#### What it costs: queries and time, compat against v2

Both dispatched through the real HTTP kernel (so middleware, storefront resolution and serialisation are
counted), on the scratch copy of production, caches warm — the state a live shop is in. One warm-up, then five
runs; the median is reported.

| Request | queries | median | products |
|---|---|---|---|
| compat `catalog/listing`, whole catalogue | 1 | 31 ms | 1,014 |
| **v2 `products`, whole catalogue** | **6** | **19 ms** | 1,014 |
| compat `catalog/listing`, one sub-type | 1 | 27 ms | 21 |
| **v2 `products`, one sub-type** | **6** | **18 ms** | 21 |
| **v2 `products`, THREE sub-types** | **6** | **18 ms** | 59 |
| compat `catalog/listing`, movement filter | 1 | 32 ms | 534 |
| **v2 `products`, movement filter** | **6** | **19 ms** | 534 |

**Budget: 7 queries and 250 ms warm.** v2 is at **6 queries** — the existing `V2\QueryBudgetTest` already
asserts ≤ 7, and the three new watch-spec facets and the multi-path category did **not** add a query, because
the facets are built as one grouped sub-select each inside the same pass. It is at **19 ms**, comfortably
inside the budget.

The query counts are not comparable as a quality measure and should not be read as a regression: **compat does
one query because it loads a cached snapshot of the whole catalogue and filters it in PHP**; v2 does six
because it filters and counts in SQL. That is why v2 is the faster of the two despite six times the queries,
and why its cost does not grow with the number of filters — the three-sub-type union costs exactly what one
sub-type costs. compat's does not grow either, but it pays the whole catalogue on every request regardless.

Cross-check that the move is faithful on the single-path case: compat `subTypes=1` and v2
`category=watches/diver` both report **21** products, and compat `movements=1` and v2 `movement=1` both report
**534**.

The product page and cart numbers are not in this table because neither has moved yet: the product page is the
second half of slice 1, and the cart is slice 3. They will be measured against the same budget when they do.

You asked for it as a rule, not an exception, and it is one: `FilterSection` returns nothing below **2**
options. One option is not a filter — ticking it returns the same products, for the price of a heading, a row
and a decision. A section whose second value appears later starts drawing again on its own, with no code change.

Nothing is hidden that a shopper could have used. A zero-count value never drew in the first place (`build()`

### Slice 1, second half — the product page: the gap report FIRST (2026-10-23)

The rule I wrote for myself after the two overruns — *before moving a screen to v2, diff what v2 serves against
what that screen's controls already do on compat* — applied here before a line was changed. It found three real
gaps and cleared one I had wrongly suspected.

**First correction to the plan: Brand Fashion's product PAGE is not the model.** Only its `serverV2.js` is. Its
`app/(main)/product/[slug]/page.jsx` renders `BfProductPage`, not the shared `ProductDetailClient`, and it
**deliberately dropped** what Watchizer cannot drop — its own comment says so: "the legacy raw-title redirect of
the copied page is not carried — recorded". Brand Fashion is not indexed; Watchizer is, and is live.

**Second: the product page is TWO reads, not one.** The server fetches `catalog/product` for SEO and the
above-the-fold card, and then `ProductDetailClient` fetches the FULL record itself from the browser —
`products/{id}`, or `products/by-name/{param}` for a legacy URL (lines 173–198). Moving only the server read
would have moved half the page.

#### What v2 serves against what the screen already does

| the screen, on compat | v2 | verdict |
|---|---|---|
| server: `catalog/product?slug=` → cards, meta, images, ratings | `products/{slug}` → product + related + locale, resolved and localized | **v2 is a superset** |
| client: `products/{id}` → the full flat record for specs and gallery | already inside `products/{slug}` | **v2 removes a round trip** |
| watch spec rows, built in the browser from ~20 flat columns and their `_ar` siblings | `specs[]` pre-built: `{key, label:{en,ar}, value, unit}` | **v2 is better** — labels and units come from core |
| resolve by **numeric id**: `catalog/product?slug=437` → **200** | `products/437` → **404** | **GAP 1** — v2 is slug-only |
| resolve by **legacy raw title**: `products/by-name/COACH Women's Signature Canvas Medium Corner Zip Wallet CW786` → **200** | no endpoint at all | **GAP 2** — no v2 equivalent |
| family extras on the 20 products that have them | served, but see below | **GAP 3** — labels, units and booleans |
| `catalog/related` rail | `products/{slug}/related` → 200, and `related` is embedded in the detail payload | present |
| the reviews list and posting a review (`all_product_rating`, `add_product_rating`) | nothing | **stays on compat** — slice 6, out of scope by the brief |

**A gap I suspected and disproved, because I measured it.** The first non-watch product I checked came back
from v2 with an empty `specs[]`, which looked like the watch-filter mistake all over again — v2 not serving what
the screen shows. It was not: that product has no extras on compat either. `ProductDetail::familySpecs()` does
read `catalog_products.specs`, and **all 20** products that carry legacy `extra_attributes` have those keys
present in the clean-core column, identical, nothing lost in the migration. A wallet comes back from v2 with
all six of its rows. Had I reported from the first product I would have invented a data gap that does not exist.

**GAP 3, the real one, is the labels.** `familySpecs()` builds a row's label as

#### The decisions taken, not blocked on

**D1 — the product page reads v2 first and keeps compat as its fallback chain.** v2 `products/{slug}`, and when
v2 does not know the slug: compat's slug lookup, then compat's by-name, then the brand-page 308, then 404 —
exactly the ladder that exists today. *Why:* gaps 1 and 2 are live indexed URLs on a shop Google crawls. *The
alternative* — move cleanly and let legacy URLs 404 — would drop real products out of the index to make one
file tidier. *Cost:* the product page keeps a compat dependency, listed below, and it is only ever reached when
v2 says no.

**D2 — `/products/[id]` stays entirely on compat.** It is a redirect-only route (numeric id → canonical 308)
and v2 has no id lookup. The brief says to leave an endpoint with no v2 equivalent on compat and list it rather
than invent one, so that is what this does.

**D3 — the browser's full-record fetch is removed.** The server already holds everything v2's detail payload
carries, so it hands it to the component instead of the component asking core a second time. The product page
goes from two upstream reads to one. This is the measurable win of the half-slice, and it is only possible
because v2's payload is the superset the table above shows.

**D4 — the curated family-spec labels move into core** (gap 3), not into the adapter. A label that belongs to a
field belongs with the field.

**D5 — reviews stay on compat.** `all_product_rating` and `add_product_rating` have no v2 equivalent and
ratings are explicitly slice 6. Listed, not built.

## Addition B — the colour and size pickers, designed for Watchizer

### The ground truth, measured before designing

| | |
|---|---|
| Visible Watchizer products with **no variants** | **981 of 1,014** — so "the page looks exactly as now" is the case that matters |
| colour only / size only / colour **and** size | 14 / 1 / 18 — all four cases exist to build against |
| ...of which carry **real** (non-demo) variant rows | **0** |

Every variant product on either storefront is one of the 33 `DEMO-` rows. The 24 products with genuine size
variants belong to Brand Fashion and are `is_visible = 0`. **No live Watchizer product has a variant today**,
which is both why this is safe to ship and why it cannot be proven against real stock yet.

### Two things the rule found, before building

**A blocker, not a gap: the compat cart refuses variants outright.** `CartCompatController` answers any
product with `has_variants` with a 422, *"This product requires selecting an option"* — unconditionally,
whether or not a `variant_id` is sent. Watchizer's cart is compat, so **a picker cannot complete an
add-to-cart until slice 3**. Its own comment says the refusal is "unreachable on Watchizer (no storefront-1
product has variants)", which the measurement above confirms is still true.

**GAP 7, on the storefront side this time: the cart line key has no variant dimension.** `getItemKey` keys a
line by `product_id` alone. Core's cart key already carries `variant_id` — "the same shirt in two sizes is two
lines", wave 3.5 — but the storefront's does not, so a shopper adding a second size would have found the first
line by product and **incremented it: the wrong size, silently**.

### The decisions

**D8 — the picker ships now; the add completes in slice 3.** The display, the selection, the availability
narrowing and the variant's own price and stock are complete and proven here. The add-to-cart proof belongs in
slice 3's proof bar, where your brief already puts "a real end-to-end order with a VARIANT product". Nothing
can regress for a shopper meanwhile, because no live product reaches the picker.

**D9 — `getItemKey` is NOT widened here.** Compat deletes a cart line by product, so adding a variant
dimension to the key now would make it miss lines, on a live cart, for no gain while compat refuses variants
anyway. Instead the picker simply never merges: **when a variant is chosen, the add does not look for an
existing product-keyed line.** That closes gap 7's actual failure without touching the cart. The key is
widened with the v2 cart, in slice 3.

**D10 — the sold-out chip is inert.** Clicking one would select a combination that cannot be bought, leaving a
disabled button and nothing saying why. Clearing the other axis un-strikes it, which is the normal way back.
The alternative — clicking a struck chip clears the other axis — is more clever and less predictable; it is
noted here, not built.

### The design, and why it is not Brand Fashion's

Brand Fashion's picker is circular hex swatches and rounded pills — its own language, from its own visual
reset. Watchizer's product page has two habits of its own, and the picker is built out of them rather than
imported:

* **the spec table's label/value pair** — a term on one side, its value on the other. Each axis is headed that
  way: `COLOUR` on one side, `Silver` on the other, over a hairline rule. An axis therefore reads as *a spec
  row whose value you can change*, which is what it is.
* **the quantity stepper's control** — a 6px hairline box on white, cream `#f1ede5` on hover, pressed at 0.96.
  The chips are that control, one step smaller.

The chosen chip takes **the add button's ink fill**, so "selected" and "what the button will act on" are one
statement in one colour rather than two inventions. That is the single bold moment; everything else is
hairline and quiet — no shadow, no gradient, no motion beyond the page's existing 0.15s.

A colour chip carries **its swatch and its name**. A watch buyer chooses "Navy", and a word is what a screen
reader announces and what the Arabic page translates; a bare circle is neither. The swatch is a 13px **square**
with an inset hairline — so white and silver read on a white chip — not a circle, which is Brand Fashion's.

A sold-out value is **struck through, not hidden**: hiding it tells the shopper the size does not exist, when
it exists and is merely gone today. The words "Sold out" are given to screen readers only — on screen the
strikethrough already says it, and printing it made the row ragged, a colour chip carrying a name *and* a
status being twice the width of its neighbours. One statement per state.

### Proven by exercising the page, not by reading the code

Clicking through the colour-and-size product at 1440 px:

| step | Colour | Size | message | add | stock shown |
|---|---|---|---|---|---|
| nothing chosen | Not chosen | Not chosen | Choose a colour and a size | disabled | 24 — the product's |
| Silver | **Silver** | Not chosen, **M struck through** | Choose a size | disabled | 24 |
| Silver + S | Silver | **S** | — | **enabled** | **4 — the variant's** |

the stock line drops from the product's 24 to that row's 4 once the combination is settled. The price follows

| case | result |
|---|---|
| colour only (3 colours) | one axis, "Choose a colour", add disabled |
| size only (36mm / 40mm / 44mm) | one axis, **40mm struck through**, add disabled |

**Arabic RTL** — the label/value row mirrors (اللون right, فضي left), the chips flow right to left, the swatch
sits on the leading edge, and the struck size reads إم. The whole flow was exercised in Arabic, not merely
screenshotted: اختر اللون والمقاس → اختر المقاس → enabled.

**Phone, 390 px** — three colour chips on one row, 40px touch targets, no horizontal scroll.

**Dark — a finding, not a tick.** **Neither storefront has any dark theme.** There is no `prefers-color-scheme`

### Survey item 8 — the marquee under the social icons

**It was a real defect, and not where the CSS said it was.** The wrapper already carried
`padding-inline-end: 60px` and a fade, and had since before the survey — so the obvious reading was "already
fixed". Measured at 1440 before touching it: the icon cluster spans x=1320–1361 and the marquee's **visible**
region also ended at 1361, so the text ran under the icons for their whole width.

Two causes, both invisible in the CSS as written:

1. **`overflow: hidden` clips at the PADDING box.** Padding does not keep overflow content out, so the track
   painted straight through those 60px.
2. **The fade was a percentage of a wrapper that reached behind the icons.** `black 92%` put the fade's start
   at x≈1257 and its end at 1361, so at x=1320 — where the icons begin — the text was still about **39%
   opaque**. That is the "DELIVERY ACROSS EGY**P**" overlap.

Now: the icons' width is reserved with a **margin** (`--wz-strip-social-space: 76px`), which moves the border
box so the clip ends before them; and the fade is stated in **pixels** (40px at each end) so its length does
not change with the viewport. Measured after: the marquee's clip ends at 1285, the icons start at 1320 — a
**35px gutter**, identical at 1920 and 1024, and the strip is not drawn at phone width at all.

### Survey item 14 — a rail needs four products

`>= MIN_RAIL_PRODUCTS`, which is **4** — one full row of cards at desktop width. Measured against the live

on the line and still draw.

**(b) In the dashboard — D11: FLAG, not refuse.** The owner's instruction allowed either and asked which and

* A flag tells the truth **continuously**: at save, and in the list, every time it is looked at.

*The alternative* (refuse) would have cost a blocked workflow and a false sense of a guarantee. So the Home

### 4 — follow-redirects 1.16.0 (CVE-2026-111755, CVE-2026-111756)

* Pulled in transitively by `axios@1.20.0` (`^1.16.0`) in both apps; nothing of ours depends on it
  directly.
* Fixed with an override, so a fresh install can never resolve the vulnerable line again:
  `follow-redirects: ">=1.16.1"` in **`pnpm-workspace.yaml`** (pnpm 11 ignores `package.json#pnpm`
  with a warning — measured). Both lockfiles re-resolved: the override line plus 1.16.0 → 1.16.1,
  **nine lines each and nothing else**; `pnpm why`: one version, 1.16.1; `pnpm install
  --frozen-lockfile` accepts both.
* Exposure, honestly: the browser's axios follows the browser's own redirects, so this is Node-side
  only. `serverFetch.js` sends the secret `X-Storefront-Server-Key` and `Api-Code` to the Laravel
  origin with axios's default `maxRedirects`, so a cross-origin 3xx from the origin WOULD have carried
  them. The origin issues no such redirect in normal operation; it is patched anyway.
* A trap worth the memory it got: `pnpm install` answered "Already up to date" for a lockfile restored
  from git, with `--force` and with `--frozen-lockfile` too — its state file
  (`node_modules/.pnpm-workspace-state-v1.json`) was trusted over the lockfile. Moving the state file
  aside made it re-resolve; the unrelated `nanoid`/`postcss` bumps in the first diff came from an
  install run with a mangled workspace file, not from the override.
