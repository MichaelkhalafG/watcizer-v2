## 5. If you have to roll a migration back

> **CORRECTED 2026-10-21.** This section used to cover only migration #4. The other three had **no way back
> at all**, which matters more than usual here because `php artisan migrate:rollback` is **forbidden in this
> application, in every environment** — `AppServiceProvider` calls `DB::prohibitDestructiveCommands()`,
> because the database is shared with the legacy app. An uncovered migration meant no rollback existed.
> All four are covered below, and every statement has been run and verified on a copy.

**Roll back in REVERSE order, and only the ones you actually need.** They are independent: #1, #2 and #3 are
additive and cannot break the live site, so the realistic case is **#4 alone**.

### #4 — the orders backfill (the only one that adds a constraint)

```sql
-- the ids come from storage/app/orders_storefront_backfill.json
ALTER TABLE `orders` MODIFY `storefront_id` BIGINT UNSIGNED NULL;
UPDATE `orders` SET `storefront_id` = NULL WHERE `id` IN (1,2,3,4,5,6,7,8,9);
DELETE FROM `core_migrations` WHERE `migration` = '2026_10_23_000000_orders_storefront_backfill';
```

Verified: 9 rows null again, 20 on storefront 1 — the original split exactly — column nullable, ledger row gone.

**Do not** `UPDATE orders SET storefront_id = NULL WHERE storefront_id = 1`. That would untag every Watchizer
order ever placed. Only the nine recorded ids.

### #3 — the open-queue index

```sql
ALTER TABLE `orders` DROP INDEX `orders_status_sf_created_idx`;
DELETE FROM `core_migrations` WHERE `migration` = '2026_10_23_000000_orders_open_queue_index';
```

Verified: index present → absent. Loses nothing; the dashboard's work queue simply gets slower (72 ms rather
than 34 ms at 250,000 orders).

### #2 — the home hero key

```sql
UPDATE `storefronts` SET `settings` = JSON_REMOVE(`settings`, '$.home.hero')
 WHERE JSON_EXTRACT(`settings`, '$.home.hero') IS NOT NULL;
UPDATE `storefronts` SET `settings` = JSON_REMOVE(`settings`, '$.home')
 WHERE JSON_EXTRACT(`settings`, '$.home') IS NOT NULL AND JSON_LENGTH(JSON_EXTRACT(`settings`, '$.home')) = 0;
DELETE FROM `core_migrations` WHERE `migration` = '2026_10_22_000100_storefront_home_hero';
```

Verified: the `hero` key and then the emptied `home` key removed on both storefronts, with `promotions` and
`identity` untouched. **Watchizer stays on the 3D hero either way** — an unset value reads as `three_d`.

*One nuance:* the migration's `up()` skips a storefront that already names a mode, but its `down()` removes
the key unconditionally, so a rollback can clear a value that pre-dated the release. Harmless today, because
both storefronts were unset before it ran.

### #1 — the banner columns ⚠️ THE ONLY ONE THAT DESTROYS DATA

```sql
ALTER TABLE `storefront_banners` DROP COLUMN `device`, DROP COLUMN `image_original_path`, DROP COLUMN `crop`;
DELETE FROM `core_migrations` WHERE `migration` = '2026_10_22_000000_banner_device_and_crop';
```

Verified: three columns present → absent.

**This throws away every banner crop an operator has set since the deploy, and nothing brings them back.**
#2, #3 and #4 lose nothing; this one does. Do not run it to tidy up — run it only if the banner columns are
themselves the problem.
