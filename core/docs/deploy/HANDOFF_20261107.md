didn't match the client` (the App Router of Next 15 runs React 19's canary whatever `package.json` says — 18.3.1 here).
"HTML" (not "text") means a structural difference: an element present on one side only.

**Method.** `hydra.mjs` (headless Chrome over CDP): a fresh profile per visit, the page loaded at 390×844 (touch, DPR 2)
and 1440×900, the Cairo time zone, every console error and thrown exception kept WHOLE, hydration waited for (a React fiber
on `<header>`), a scroll through the page, the floating boxes read; `--via=/` first loads another page in the same tab, so
the second page has whatever sessionStorage and the query cache kept — **without that option neither fault shows**, which
is why a plain reload in dev never found it. `--storage=k=v` sets the Hot Deals mode; `--cookie=ar` the language.

**Reproduced (dev build, the full message with the component stack):**

1. `/hot-deals` and `/flash-sale` in their idle state, as the second page of a visit, phone and desktop: the client's
   first render ADDED `<nav class="pm-idle-nav" aria-label="Shop by category">` the server HTML lacked. The categories
   came from `useMenu`'s `initialData` — the sessionStorage copy only the browser has.
2. `/` and `/ar`, with a campaign live, as the second page of a visit, phone and desktop: in `CategoryTiles › ChipPicture`
   for "Power Banks" the server rendered `<span class="wz-cat-chip-initial">` and the client `<img class="wz-cat-img
   wz-cat-img--product">`. A probe printed from the server render showed `menu undefined, fallbacks 0` — the page's
   `HydrationBoundary` carried the menu (it is in the HTML's dehydrated state) but the server render of the row never
   saw it: the header's `MegaMenu` had created the menu query first (`useMenu(false)`), and React Query hydrates an
   EXISTING query in `useEffect`, never during render. The browser's first render then had the storage copy. The live
   home is ISR for five minutes and every returning visitor has the copy, which is why Michael saw it on the home.
3. Not reproduced but certain from the code and fixed with the same rule: the countdowns' `Date.now()` first render
   against HTML held for minutes (an ended campaign; the day boundary's `3d` and day box — a SHAPE change no
   `suppressHydrationWarning` covers). Proved absent after the fix by the ISR case in §7.1 (a sale ending 100 s after the
   home was cached).

**Checked and cleared** (the brief's list): the Hot Deals switch and mode read storage through `useSyncExternalStore`
with a server snapshot of "off" (no mismatch, and the mode is applied after hydration); the cart and the auth stores read
storage after mount; `FeaturedBanner` shuffles after mount; the 3D canvases are `ssr: false`; the product card's "New"
badge compares `Date.now()` against `created_at` + 14 days (a boundary crossing inside a five-minute ISR window is
possible in theory, once per product, and no page type showed it in 60 loads — left as is); `toLocaleString('ar-EG')`
prints the same digits in Node and Chrome (no text mismatch seen in Arabic); held reads differing from the client's fresh
fetch — the layout seeds the campaigns and the client's first render uses exactly that copy (the refetch comes later).

**Fixed at the cause (twins unless named):**
- `app/(main)/page.jsx` + `HomeClient.jsx` (Watchizer): the menu is a PROP of the page's server render, handed to the
  category row, and the query cache is seeded from it after mount (the header's menu is still ready before the first
  hover, with no request). The boundary is gone (the data was in the HTML twice).
- `CategoryTiles.jsx`: takes `menu` as a prop; the hook is a cache reader for a caller that passes nothing.
- `hot-deals/page.jsx`, `flash-sale/page.jsx`: pass `idleMenu(menu)` (slug, path, name per top-level category, ~300 bytes)
  to `CampaignPage`, which takes it as a prop for the idle list.
- `usePromo.js › useMenu`: no `initialData`; the kept copy enters the cache in an effect when the cache has no menu.
- `campaign.js › slimCampaigns` keeps `now`; `usePromo.js › useLiveCampaign` starts "now" at the answer's own second and
  returns `serverNow`; `Countdown.jsx` takes `now` for its first render and ticks from the device's clock after mount —
  `suppressHydrationWarning` removed from both countdown variants; `CampaignRail.jsx`, `CampaignNav.jsx`,
  `CampaignPage.jsx`, `SalePane.jsx` pass it.
- Zero layout shift by construction: every first render is the server's own.

**Proof:** §7.1 — the production builds, every page type, phone and desktop, English and Arabic, with the campaigns live,
with Hot Deals mode on, after a campaign ended inside the cached HTML, and with no campaign at all; both shops; every page
as the second page of a visit. Also the dev build before the fix (the two reproductions above) and after (0).

**The flow, as built:** `/spin?utm_…` → the landing's tags kept for the session → the phone (01xxxxxxxxx, Arabic digits
and +20 accepted) → `POST wheel/spin` {phone, device, locale, utm} → core decides (`random_int(1,100)` over the odds),
creates the prize rule if it is not there, inserts the spin, answers `{status: new, spin}` → the page turns the disc
(five turns and a bit, a deterministic offset per code, `cubic-bezier(0.12,0.78,0.16,1)` over 5.2 s, the pointer ticking
on each separator) → confetti → the card. `already_spun` (the same phone again, in any spelling) → the card at once
with "this number has already spun". `device_limit` (another phone from the same handset) → the sentence.
`wheel_off` (410) → the ended state. The card is remembered on the device (`wz_wheel_spin`) and refreshed from
`GET wheel/spin?phone=` behind it (used / expired). The code typed in the cart: "Code applied" + the note with the
masked phone; at the checkout, typing another number → the sentence naming both numbers (masked), the code kept; the
right number → applied; placing the order with the wrong number is refused by core with the same sentence (nothing
written); with the right number the order carries the discount, the redemption names the spin's code, the spin records
the order, and a second order with the code is refused ("already used on order …").
