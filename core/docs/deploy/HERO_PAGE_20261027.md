## 1. The reference: https://thewatch.60fps.fr/ (Part A.1)

### 3.3 The rules the page is built on (each with a test)

1. **The database wins.** Every figure is a spec row or a colour from the v2 answer, label and unit included; the brief's figures are nowhere in the page. A VERIFY key the record holds prints the record; one it lacks prints a placeholder row.
2. **The shop's price contract.** `sale` counts only when `0 < sale < selling` — the cart's and the card's rule — so the page cannot quote a sale the cart would refuse at checkout (`Order total mismatch`).
3. **The product page's cart line, field for field** — `product_id`, `quantity`, `piece_price` (the final price), `type_stock` express-before-market, the colour finish as hexes joined by `/`, the English name for analytics; added through `cartStore.addItem` (an existing line gets `updateQuantity`), so the existing `AddToCart` / `add_to_cart` events fire from the store **after the server confirms** exactly as on the product page. **No new event name.**
4. **The product page's Product JSON-LD**, by construction (the same adapter, transform and builder over the same answer): asserted equal in both languages.

## 4. Banner, hreflang, sitemap (Part A.4, B.1, B.5)

### 4.1 Can a banner link to an arbitrary internal URL from the dashboard today? (A.4)

**Yes.** `BannerWriter` (core) accepts a target `url` whose `link_url` is **a relative path (`/…`) or an absolute http(s)
URL** — `preg_match('#^(https?://|/)#i')` — and `HomeBanners::href()` serves it as given; the storefront's `BannerHero`
localises it (`localizeHref`). So `/experience/hugo-boss-grand-prix-1513477` is accepted as typed.

**What was NOT possible without code:** Watchizer's home draws the dashboard's banners **only when its hero is `banner`**
(`settings.home.hero`; Watchizer is `three_d`, measured on the dev copy of the storefronts table) — a banner would have
replaced the 3D watch. **The smallest change, made:** `HomeClient.jsx` draws the same `BannerHero` **under** the 3D hero
when the hero is `three_d` and at least one active banner exists; with none — Watchizer today (zero banner rows) — the
home is byte-for-byte what it was. A twin, changed on both sides identically (Brand Fashion's hero is `banner`, so its
home does not take the branch).

**The banner itself needs Michael (B.5):** on the dashboard's Banners screen, storefront Watchizer → New banner → the
image (desktop and/or mobile — I sourced none), target **URL**, link `/experience/hugo-boss-grand-prix-1513477`, active.
`catalog/home` is cached 60 s at the CDN and 5 min by the page's ISR.

### 4.2 Route, hreflang, canonical, metadata (B.1)

As every two-language page: `/experience/…` is English and self-canonical, `/ar/experience/…` Arabic and self-canonical,
both carrying `hreflang` en, ar and `x-default` (English); the middleware's rewrite serves the Arabic one. Title and
description are the page's own (not the product page's), the og image the recorded cover.

### 4.3 The sitemap — a recommendation, not a decision (B.1)

The storefront's `/sitemap.xml` is core's `CompatLocaleSitemap`: `/`, `/listing`, the four trust pages
(`TRUST_PAGES`), the categories and the products — so listing this page is **a core change** (one path in a list, plus a
test) **and a core deploy**, not a storefront one. Recommendation: **add it in the next core deploy, after D4 is resolved**
— the page is indexable and self-canonical, its text is its own (not the product page's), and the product page stays the
offer's URL in the structured data, so there is no duplicate-offer risk; until then the home banner and the breadcrumb
link it. The alternative — keep it out and let the banner carry it — costs nothing and is reversible. Michael decides.
