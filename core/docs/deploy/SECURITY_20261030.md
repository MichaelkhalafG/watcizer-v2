## 4. The `transformAlgorithm` error (3 × 2026-10-29 13:03 UTC)

`controller[kState].transformAlgorithm is not a function` is a **Node.js** web-streams bug, not Next's:
nodejs/node#62036 — a write pending on back-pressure runs after the stream was cancelled (typically a visitor who
disconnects mid-response) and calls a cleared function. Fixed by nodejs/node#62040, released in **Node 24.15.0** (and
25.8.1). The Next upgrade does not touch it. Next's own process handlers log such errors and carry on (§5), so it is
noise, not a crash. **RECOMMENDATION:** set both Node.js apps to Node 24 (24.15 or later) in hPanel — the storefront
runbook records the host building with Node 22 (`RUNBOOK_PHASE2_STOREFRONT.md` line 1534); every local build and
test here ran on Node 24.16.0. Your decision; check the version hPanel offers first.

## 5. The process log (for the restarts of 2026-10-30 10:06, 10:08, 10:23 UTC)

New twins: `instrumentation.js` (Next calls `register()` once when the server starts, Node runtime only) and
`src/lib/processLog.js`. One JSON line on **stderr** per event:

```
{"ts":"2026-10-30T11:11:01.429Z","event":"start","app":"watchizer","pid":15728,"uptime_s":0.8,"rss":90279936,"heapUsed":36377184,"node":"v24.16.0","port":"3020"}
```

Events: `start` (with the Node version and `PORT`), `uncaughtException` (with origin, name, message, stack),
`unhandledRejection`, `SIGTERM`, `SIGINT`, `exit` (with the exit code). Every line carries `ts` (ISO), `app`, `pid`,
`uptime_s`, `rss` and `heapUsed`.

**It logs only; exit behaviour is unchanged** (measured on a real Node process, not only the unit tests):

- What Next does today (read from `next/dist/server`): `next-server.js` and `router-server.js` install listeners for
  `uncaughtException` and `unhandledRejection` that LOG AND CARRY ON — an error inside the app does not stop the
  process; `start-server.js` handles SIGTERM/SIGINT by closing the server and `process.exit(0)`.
- Ours watches uncaught exceptions through `uncaughtExceptionMonitor` (observes, never handles); adds one more
  `unhandledRejection` listener beside Next's (re-throws if it is ever the only one — what Node does with none);
  prepends SIGTERM/SIGINT listeners that log and return (re-raise the signal if ever alone); writes the exit line
  with `writeSync`.
- Real process: alone, a thrown error → our two lines + Node's trace, **exit 1** (Node's own); a lone rejection →
  **exit 1** (Node's own); `process.exit(3)` → exit line `code: 3`, **exit 3**; beside Next-style listeners, a throw
  and a rejection are both logged and the process **stays up**, as today.
- `tests/processLog.test.mjs` (10 tests, both apps): the line's shape, once per process, monitor-not-handler,
  rejection with and without another listener, SIGTERM order (ours first, Next's decides), SIGINT alone re-raised,
  the exit code, a failing writer never throws.

**Reading it on the server:** hPanel → the Node.js app → its build directory `hbuilds/versions/<current>/nodejs` →
`stderr.log` (these lines) and `console.log` (Hostinger's restart banners and Next's "Ready"). How to read a restart:

- `SIGTERM` then `exit` `code: 0` — the host asked the app to stop (a restart or a redeploy by the platform).
- `uncaughtException` / `unhandledRejection` lines — an error inside the app; Next keeps running after them, so they
  explain errors, not a stop, unless an `exit` follows.
- `exit` with a non-zero code — the app ended itself (for example `code: 1` when the port was taken: Next starts with
  `allowRetry: false`).
- a `start` line with **no `exit` line before it** — the process was killed outright (SIGKILL, the out-of-memory
  killer, the host's watchdog). Nothing inside a process can log that; the gap itself is the evidence, and the `rss`
  of the last lines before it says whether memory was climbing.

## 6. Port and process model

- **Code:** Hostinger builds a STANDALONE server (`pnpm-workspace.yaml`'s comment, measured 2026-10-11). Next 15.5.28's
  standalone `server.js` (template in `next/dist/build/utils.js`) chooses `parseInt(process.env.PORT, 10) || 3000`,
  host `process.env.HOSTNAME || '0.0.0.0'`, `allowRetry: false`, and calls `startServer` once: one HTTP server in one
  process. Nothing in either app forks (no `child_process`, `cluster`, `worker_threads` or PM2 in `app/`, `src/`, the
  config or the scripts). `ecosystem.config.js` (PM2 cluster ×2, port 3000) is dead config — nothing reads it
  (backlog BF-PM2-CWD). Locally `next start` ran as one process: one `start` line, its pid the launched node's.
- `package.json` `start`: Watchizer `next start` (PORT or 3000); Brand Fashion `next start -p 3001` — a hard-coded
  port that would OVERRIDE a `PORT` from the host. It is the local-dev convenience (beside Watchizer on 3000); it is
  wrong only if Hostinger runs `pnpm start` for Brand Fashion instead of the standalone `server.js`. Not changed.
